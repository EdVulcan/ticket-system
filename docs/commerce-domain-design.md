# 商业交易域设计记录

> 状态：基础模型、迁移、租户能力边界、商品/SKU/规格/库存、订单/支付状态、餐饮与电商履约、退款服务及租户后台工作台已完成本地实现（2026-09-17）。真实支付适配、游客/公开渠道入口、通知和生产履约 worker 尚未接入，不能据此宣称商业域生产就绪。
>
> 本文是现有多租户开发基线的商业交易域细化记录，不替代项目技能、开发基线、审计和路线文档。若本文与基线冲突，以基线和平台硬边界为准。

## 1. 目标与范围

本域为同一 SaaS 平台中的独立业务域，当前包含两个业务模块：

- **餐饮**：菜品、规格、购物车、外卖订单、自取订单和简单配送。外卖是餐饮模块下的履约方式，不建立“外卖租户”类型；后续堂食或扫码点单也属于餐饮域的子能力。
- **通用电商**：面向一般实物商品，不限定为冷吃商品。包含商品、SKU、规格、库存、购物车、收货地址、支付、发货、物流和售后。

这两个模块从商品模型开始重新规划，不把景区票务商品改造成万能商品。票规、票码、检票点、核销次数、景区票库存和票务结算继续属于景区票务域。

## 2. 平台与租户边界

### 2.1 共用 SaaS 内核

以下能力继续由平台内核提供，商业交易域通过明确的服务接口使用：

- `Tenant`、用户、员工、角色、权限和租户状态；
- 渠道账号、游客身份、渠道请求幂等和渠道回调入口；
- 支付适配、支付通知、退款任务、资金审计和不可变金额事实；
- 通知、媒体存储、操作审计、任务重试和运行告警。

共用不代表共用业务表的含义。支付和退款适配器可以复用，订单、履约和售后事实仍由所属业务域负责。

### 2.2 租户身份与经营业务分离

供应商、分销商和旅行社是租户市场身份/能力；景区、酒店、餐饮和电商是租户经营业务。不能新增互斥的 `tenant_type` 来表达这些组合。

系统管理员在租户管理中独立开通或暂停业务能力：

```text
租户 A
├── 身份/能力：供应商
├── 经营业务：景区票务
└── 经营业务：餐饮

租户 B
├── 身份/能力：供应商
└── 经营业务：通用电商
```

同一租户可以同时开通景区、餐饮和电商。关闭业务只停止新增相关商品、购物车和订单，不删除历史订单、退款、对账、结算或审计事实；已提交订单继续按原快照处理。

所有商户、商品、库存、订单和渠道查询都必须从认证服务端上下文取得 `tenant_id`。客户端不能通过请求体、URL 参数或渠道链接指定另一个租户。

## 3. 业务域隔离

商业交易域使用独立 API、服务边界和表前缀。建议命名方向为 `commerce_*`，餐饮和电商的专属事实分别使用 `restaurant_*`、`retail_*` 或等价命名。

禁止以下做法：

- 在现有景区 `Product` 上增加大量餐饮/电商空字段；
- 用票码、票权益、检票点或景区核销记录表示实物商品履约；
- 用一个含义不明确的全局订单状态同时表示支付、制作、配送、发货和退款；
- 让商业订单进入景区票务库存、票务结算或核销服务；
- 为新渠道复制一套租户或游客身份系统。

## 4. 商业商品与库存模型

### 4.1 商品聚合

商业商品从零建立独立的商品聚合，至少包含：

- 所属租户和业务域（`restaurant` 或 `retail`）；
- 商品名称、短标题、介绍、媒体、分类、上下架状态和销售时间；
- 一个或多个销售 SKU；
- 业务域专属资料和履约地点；
- 当前版本或更新时间，用于防止编辑覆盖已售快照。

商品图片、商品介绍和渠道陈列图片继续分开维护。小红书商城头图等渠道陈列字段只影响对应渠道，不回写商业商品事实。

### 4.2 SKU、规格与选项

SKU 是价格和库存的最小销售单位，价格统一使用整数分。下单时保存商品、SKU、规格文本、选项、数量、单价、优惠分摊和媒体/介绍快照。

- 电商规格主要表达口味、重量、颜色等可售组合；
- 餐饮规格既可以形成 SKU，也可以包含必选/可选的加料、口味和份量选项；
- 选项的价格和可售状态必须由服务端从当前商品版本计算，客户端只提交受限的选项引用。

第一版不做游客自由组合跨商品套餐，不把餐饮加料和电商 SKU 价格交给客户端决定。

### 4.3 库存

库存按租户、业务域、SKU 和履约地点隔离，至少区分可售、预占、已售和释放事实。购物车不直接扣减库存；下单时原子预占，未支付超时只释放一次，支付成功后转为已售。

餐饮库存可按门店/制作地点管理；电商库存可按仓库/发货地点管理。第一版可以各限制为一个履约地点，但表和服务接口不把订单永远写死为单地点，后续扩展不应改写历史订单。

## 5. 购物车与订单

购物车必须绑定：租户、业务域、游客/客户、渠道账号（如有）和履约地点。一个购物车只能属于一个租户和一个业务域：

- 景区门票、餐饮、电商不能混在一个购物车；
- 餐饮和电商即使属于同一租户，也不能混单；
- 不同门店、仓库或配送主体不能混在一个订单。

商业订单与票务订单独立建模。商业订单至少记录租户、业务域、渠道、客户、金额快照、联系人/地址快照、支付引用和售后引用；订单明细保存商品、SKU、规格、数量、价格、优惠和媒体/介绍快照。

订单、支付、售后和履约是相互独立的状态投影。支付回调、客户端重试、后台操作和进程重启都必须通过持久化幂等键收敛，不能只依靠前端按钮或内存状态。

## 6. 两套履约状态机

### 6.1 餐饮履约

餐饮订单的履约状态建议为：

```text
待接单 → 已接单 → 制作中 → 待取/待配送 → 配送中 → 已完成
             └──────────────→ 已取消
```

自取订单不进入配送中；配送订单必须有有效收货地址和配送范围校验。商家接单、拒单、完成制作、标记出餐和完成配送分别受权限控制并写入操作记录。

首版只要求简单配送/自取闭环，不建设骑手调度、复杂路线、平台配送结算或堂食桌台收银。配送费、配送区域、预计时间和拒单超时规则在实现前另行确认。

### 6.2 通用电商履约

电商订单的履约状态建议为：

```text
待发货 → 已发货 → 配送中/运输中 → 待收货 → 已收货 → 已完成
    └────────────────────────────→ 已取消
```

发货必须保存发货时间、物流公司和快递单号；物流状态不能伪造收货事实。第一版可限制一单一个发货履约单，但应通过独立履约记录表达，不能把快递字段散落在订单主表导致以后无法扩展多包裹。

当前范围只包含退款售后，不默认开放换货、复杂退货入库或多仓拆单；这些能力以后必须单独增加状态机和资金规则。

## 7. 支付、退款与优惠

- 商业订单复用平台支付适配和回调幂等能力，但支付记录必须明确引用商业订单；不能把票务订单号当作商业订单身份。
- 退款金额由服务端根据订单/明细快照和售后规则计算，不能信任客户端金额；退款成功后再更新商业库存、售后和履约投影。
- 退款、支付和履约状态分开保存；不能用“已完成”覆盖“退款中”或用“已退款”伪造物流完成。
- 分享助力、优惠券或其他营销活动另属促销域。首版不把营销资格、券钱包和商品价格直接写进商品表；优惠分摊写入订单快照，退款按快照回收或冲销。

## 8. 渠道与前端入口

渠道账号仍归属于租户，渠道商品映射必须同时校验租户和业务域。小红书或未来微信入口只能展示该渠道账号已发布且审核/上架可售的商品。

同一租户可在一个渠道账号下经营餐饮和电商，但目录、商品详情、购物车和订单接口必须根据业务域展示对应交互；不能把餐饮商品伪装成门票，也不能让餐饮订单走票码页面。若未来需要按门店或业务域生成外部链接，链接参数只能作为展示上下文，最终租户和商品归属仍由服务端映射确认。

## 9. 后台与权限

业务能力开通后，后台才显示对应工作台和菜单：

```text
租户管理 → 业务能力 → 餐饮 / 通用电商
餐饮 → 菜品、规格、门店、外卖/自取订单、配送设置
电商 → 商品、SKU、库存、发货、物流、售后
```

后台接口按租户和业务域授权，至少区分商品编辑、库存调整、餐饮接单、配送处理、电商发货和退款处理权限。菜单隐藏不能代替服务端校验；暂停业务能力后，历史订单仍需有受限的查询、售后和对账入口。

## 10. 兼容与非回归门槛

实现商业交易域时必须满足：

1. 只新增商业域表、索引和服务；除能力注册或通用基础设施外，不修改票务表的业务含义。
2. 旧数据库迁移先在包含真实历史票务订单、票权、库存和退款事实的数据库上演练，迁移失败自动停止，不改写旧事实。
3. 每次商业域改动都运行原有票务、核销、退款、供应商、分销、渠道和租户隔离测试。
4. 新增跨租户负向测试：商户 A 不能读取或修改商户 B 的商业商品、购物车、订单、地址、库存或售后。
5. 新增跨业务负向测试：餐饮订单不能进入票务核销，电商商品不能生成票码，票务订单不能进入发货或制作流程。
6. 验证支付重复回调、退款重复提交、未支付超时、进程重启、库存释放和订单状态恢复。
7. 前端只调用服务端计算出的价格、库存和履约状态；任何客户端传入的租户、供应商、结算或金额字段都不能成为权威事实。

在现有 P0 门槛、真实支付和现场准入条件未满足前，商业域只能作为隔离开发和测试能力，不能据此宣称整个平台生产就绪。

## 11. 实施顺序

1. 先完成业务能力、权限和域边界，不触碰票务订单与核销服务。
2. 建立商业商品、SKU、规格、库存、购物车和快照模型，并完成迁移与跨租户测试。
3. 优先实现通用电商的下单、支付、发货和售后闭环。
4. 再实现餐饮的接单、制作、自取和简单配送闭环。
5. 最后按真实渠道需要接入小红书/微信目录、通知和营销活动。

每个阶段完成后都要回看本文、开发基线和当前审计，确认没有把商业状态、金额或库存写入票务事实，再进入下一阶段。

## 12. 明确暂不做

- 票务、餐饮、电商混合购物车和混合订单；
- 多商户 marketplace、商户间分账和平台抽佣；
- 骑手调度、复杂配送网络、堂食桌台和完整餐饮 POS；
- 多仓自动拆单、复杂退货入库、换货和跨 SKU 换购；
- 未完成规则确认前的助力领券、复杂会员体系和营销自动化；
- 任何通过扩展票务商品、票码或核销接口实现商业交易的捷径。

## 13. 后续开发的上下文回顾协议

本节不是第二套业务规则，而是后续实现、审查和交接时的固定检查入口。商业交易域的具体规则仍以本文件第 1 至 12 节、平台开发基线和当前审计为准。

每次开始商业域工作前，必须按以下顺序回顾：

1. 先读项目技能、[多租户开发基线](./platform-multitenancy-development-guide.md)、当前阶段审计、开发路线和现场联调清单；再按任务读取本文件的目标范围、平台边界、订单状态、支付退款、渠道入口和非回归门槛章节。
2. 明确本次改动的租户、业务域（`restaurant`/`retail`）、渠道账号、客户、履约地点、支付和售后归属；任何归属都由服务端上下文推导，不能由客户端字段决定。
3. 先确认改动是否只落在商业域边界内。票务 `Product`、票权、票码、检票点、核销次数、景区库存和票务结算的业务含义不得因餐饮或电商需求改变；商业订单也不得进入票务核销、发货或制作流程。
4. 涉及数据库或状态机时，先写跨租户、跨业务域、重复回调/重复提交、超时恢复和能力暂停测试，再实现正向流程；迁移必须在包含历史票务事实的 PostgreSQL 副本上演练并保持可回滚。
5. 每完成一个阶段，更新本文件的状态、实施顺序或明确暂不做项，并同步更新开发基线中的入口说明；若真实支付、公开游客入口、通知、履约 worker 或现场条件尚未验收，不得把本地模型或后台接口描述为生产可用。

交接或上下文恢复时，优先检查本节和第 10 节的非回归门槛，再查看代码和未完成任务。若代码行为与本文或平台基线冲突，应暂停扩展范围，先记录冲突、补齐测试并取得明确的领域决策；不得通过复制表、放宽租户校验或增加兼容性旁路来“先跑起来”。

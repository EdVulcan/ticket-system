# 智游宝请求调度

本轮为本地实现，尚未部署。用户确认下单请求不受查询限频限制，暂定查询每秒最多两次。智游宝真实的每 IP 阈值、封禁时长和业务限流码仍需官方说明或实际失败报文确认；以下参数是可调整的试运行值，不是厂商承诺。

## 下单与查询分别处理

`SEND_CODE_REQ` 下单走独立通道，不占查询额度、不等待查询冷却。仍在请求前原子保存原有出票发送标记，结果不明时只查原单，不能因绕开查询限速而重复采购。下单响应直接保存供应商身份，不额外发起确认查单。

原单恢复、订单状态、核销明细、退款预检和取消结果查询共用 PostgreSQL 查询调度器。取图、取消尚未确认不受限，暂时也受该额度控制。所有租户、连接及运行实例默认共用 `zyb:global`，不按商家各放一份额度。每次受控 HTTP 请求单独申请许可，最大并发固定为 1；真正发送时更新最早下次发送时间，不累计突发额度，也不通过重定向绕过调度。

排队记录只存操作身份摘要、优先级、排队时间和租约，不存凭据、请求正文或游客资料。等待在数据库事务之外完成；15 秒内不能取得许可或正处于冷却时，返回明确的等待结果，让已有任务保存下次时间。旧的已结束调度记录按 24 小时保留期分批清理，订单和退款的业务记录不受影响。

## 优先级与合并

优先级由服务端决定：退款处理、已尝试出票的查单恢复为 30，新出票及退款预检为 20，手动状态查询为 10，日常状态查询为 0。每等待 30 秒增加一分，避免一直有新请求时旧任务永久排不到。

只有最近仍在等待的调用者竞争即时许可；已离开的查询不会一直占据队首。持久任务下次重试可以继续使用原排队时间。不同租户/连接和不同协议操作不混用身份。

手动“查询供应商最新状态”只标记现有供应快照待同步，同一订单重复点击不会建立多个任务。最近十秒已有查询结果时直接复用。页面轮询的是本系统保存的状态，最多自动查询二十次，关闭页面后停止；不反复请求供应商。原始退款预检不读取页面缓存来批准退款。

## 默认配置

配置位于 `backend/config/config.yaml` 的 `upstream_scheduling`，可用同名 `TICKET_UPSTREAM_SCHEDULING_*` 环境变量覆盖。配置属于整个部署，不放进每个票种重复维护。

| 配置 | 默认值 | 含义 |
|---|---:|---|
| request_interval_ms | 500 | 两次受控请求实际开始至少间隔 500 毫秒，即全局每秒最多两次 |
| cooldown_seconds | 60 | 首次确认限流后的基础冷却秒数 |
| max_cooldown_seconds | 1800 | 指数冷却上限；供应商要求更久时仍遵守 |
| today_poll_seconds | 120 | 当天、未使用订单的常规查询间隔 |
| future_poll_seconds | 3600 | 未来日期订单查询间隔 |
| used_poll_seconds | 600 | 已使用或部分退票订单查询间隔 |
| night_poll_seconds | 1800 | 夜间 22:00—次日 07:00 的普通查询间隔 |

出票任务不受普通日间/夜间轮询间隔限制，其中下单直接发送，后续取图或异常查单遵守受控额度。普通失败逐步退避；排队与限流不消耗业务失败重试次数。已确认供应商首次使用时间后不每轮重复请求核销明细。供应商和本地退款均完成后停止普通轮询，人工查询仍可排队。

## 限流与资金安全

当前只把 HTTP 429 识别为已确认限流，不凭普通业务拒绝或未经确认的中文描述猜测封禁。支持 `Retry-After` 秒数或 HTTP 日期，采用全出口共享的递增冷却和正向随机延迟；冷却后只允许一个探测请求。没有真实业务限流码样本前，不能宣称覆盖所有智游宝封 IP 响应格式。

受控取消请求未取得许可时，不写“取消已提交”；开始发送前，把业务意图与调度发送标记放在同一短事务中保存。下单不排查询队列，发送前仍必须保存“已尝试出票”。之后的超时、断线、429 或响应不明都按“可能已经送达”处理，恢复时查询原单，不自动重发采购或取消。

退款预检排队时还没有创建退款；已创建退款遇到排队时继续保持所有票券锁定，仅调整任务执行时间。排队不是管理员特殊退款理由。状态查询不会确认资金到账。

## 部署和观察

schema 120 新增两张调度表，并为原供应快照新增手动同步时间和失败计数。升级不会改变已有票码、订单金额、供应身份、核销或退款记录。

同一出口的实例必须使用同一数据库和一致配置；部署时停止旧版本，避免旧实例绕过调度。现有单机 Actions 部署沿用停止旧服务、迁移、启动并校验 SHA/schema 的流程。其他应用若也使用相同出口 IP 请求智游宝，其流量不会自动计入本系统，应共同协调或进一步降低本系统预算。

运维可只读观察 `upstream_dispatch_waiters` 的排队时间、优先级、`transport_started_at` 和 `last_error=rate_limited`，以及 `upstream_dispatch_gates` 的下次发送时间与冷却时间；这些表不含票码明文或密钥。查看订单时可见最近查询及等待同步的最早时间。

## 本地验证

服务层、API、路由、智游宝协议与配置全量测试通过；后台构建、Go 静态检查和编译通过。专项覆盖两个调度实例争用同一额度、真实发送时刻限速、过期调用者不阻塞队列、老任务优先级提升、共享冷却、发送意图与标记原子写入、排队不写采购/取消标记及退款锁定保留。119→120 迁移用已有订单、票码、付款及供应快照核对升级前后业务摘要一致。

Windows 本地缺少 GCC，未运行 race；后续推送由 Linux CI 继续验证。没有主动触发真实供应商限流或修改生产配置；实际额度和封禁报文仍需厂商资料或自然发生的脱敏样本确认。

## 0. 当前团队专项复核（2026-08-08）

- 普通分销合作与旅行社合作已明确为两条独立关系线。团队合同不会创建或覆盖普通 `ProductOffer`，分销合作也不能被迁移或查询成旅行社合作。
- 团队合同产品价只服务团队订单；授信额度为 `0` 表示没有可用授信。由合同创建新订单时原子占用额度，绑定既有已支付订单时不再次占用。
- 团队计划、业务员、导游和车辆档案具备维护入口；团队与结算列表支持 10/20/40 服务端分页，团队另支持关键词、状态和到园日期筛选。名单只接受业务字段，票码、入园状态等系统字段由服务端归类。
- 同一已支付票权不能同时归属多个团队成员；分批入园按成员和票权加锁并保持幂等。退款后成员、入园人数和团队状态按退款事实重算，已核销后退款不再计入有效核销或核销收入。
- 团队结算按“供应商确认 -> 旅行社确认 -> 旅行社提交付款凭证 -> 供应商确认到账”流转；净应付为零时双方确认后自动结清，不生成虚假付款凭证；争议调整追加记录后重新确认，并按合同账期计算到期日。
- schema 74/75 对有效团队履约归属和成员票权归属增加唯一保护。若旧数据存在无法自动判定的重复有效团队或重复票权占用，迁移会给出诊断并 fail-closed，不静默覆盖。

以上是代码与自动化层面的闭环，不代表真实支付、打印/读卡/扫码设备、闸机、OTA 厂商协议或现场制度已经验收。

## 1. 执行结论

项目的总体技术方向没有走错：模块化 Go 单体、PostgreSQL、独立平台身份、租户作用域、供应履约与销售订单分离、票权益、产品版本、渠道账号、团队和 POS 运维模型，都符合“低运维成本的多租户景区票务经营平台”方向。

但当前实现与长期目标存在明显差异，且差异不只是“功能还没做完”。部分已经标记为落地的模型没有成为真正的授权或业务不变量，部分流程会产生错误的支付、退款、结算、核销或迁移事实。因此：

1. **阶段 0 不能视为完成，需要重新打开。**
2. **当前可以称为有价值的交易与领域骨架，不能称为三类租户可独立运营的成熟平台。**
3. **现阶段不得声明生产可用，也不应先扩展小程序、H5 或更多 OTA 适配器。**
4. **下一轮开发重点应从“继续增加模型和 API”转为“把已有模型变成不可绕过的业务边界，并补齐真实闭环”。**

按目标能力判断，项目已完成的主要是领域骨架和若干核心交易路径；按真实可运营闭环判断仍不到一半；按生产准入判断仍处于早期。最大的风险集中在支付不明、物理景区边界、能力授权、供应商报价权、退款资金回滚、结算事实和历史数据迁移。

## 4. 阶段 0 阻断项

以下问题必须在继续渠道扩展和大规模 UI 开发前修复。

### P0-1 支付中的订单会被超时任务取消

数字支付创建后，支付记录进入 `pending`，但订单仍保持 `unpaid`。超时任务只按订单状态和 `expires_at` 查找，不排除存在活动支付的订单。订单被取消后，库存和分销资金已释放；如果支付机构随后返回成功，回调会因订单已是 `cancelled` 而拒绝完成。

风险结果是“游客已扣款，系统订单已取消且无法出票”。现有支付查单任务不能修复这个状态机冲突。

证据：[`payment_service.go`](../backend/internal/service/payment_service.go#L88)、[`order_service.go`](../backend/internal/service/order_service.go#L611)、[`payment_service.go`](../backend/internal/service/payment_service.go#L339)。

修复目标：支付状态与订单预占状态必须协调；存在活动支付时不得直接释放，超时前必须主动查单；支付不明进入持久待办，最终只能收敛到“支付成功并出票”或“确认未支付后释放”。

### P0-2 `ScenicAreaID=0` 会绕过同租户景区隔离

创建检票点时，如果没有指定景区且活动景区数量不是 1，服务仍允许保存 `ScenicAreaID=0`。产品会从检票点推导景区，因此也可能得到 0。核销只有在票和检票点景区都非零时才比较，零值实际上成为通配边界。

成功和拒绝核销记录也未写入已有的 `CheckInRecord.ScenicAreaID`，无法在事后证明实际履约景区。管理端核销接口还允许任意或空 `DeviceID`，服务不验证设备与检票点归属。

证据：[`checkpoint_service.go`](../backend/internal/service/checkpoint_service.go#L50)、[`product_service.go`](../backend/internal/service/product_service.go#L234)、[`ticket_service.go`](../backend/internal/service/ticket_service.go#L88)、[`ticket_service.go`](../backend/internal/service/ticket_service.go#L134)、[`ticket_controller.go`](../backend/internal/api/ticket_controller.go#L14)。

修复目标：新业务数据的履约景区必须非零；旧零值数据先分类迁移，无法确定归属的记录进入隔离清单；核销必须校验票权益、检票点和已认证设备三者同供应商、同景区，并把景区写入核销事实。

### P0-3 租户能力和冻结状态不是完整授权边界

平台可以维护 `supplier`、`distributor`、`travel_agency` 能力记录，但产品、景区、分销和大部分团队入口只检查角色。旅行社能力记录不存在时还会直接放行。平台暂停能力后，业务不一定停止。

JWT 请求会逐次检查租户状态，但旧 OTA 和新渠道认证不检查所属租户是否冻结/关闭，订单服务也不再次校验销售租户。因此被冻结租户仍可能通过已有外部凭据继续售票。

证据：[`tenant_service.go`](../backend/internal/service/tenant_service.go#L91)、[`team_service.go`](../backend/internal/service/team_service.go#L101)、[`team_service.go`](../backend/internal/service/team_service.go#L123)、[`router.go`](../backend/internal/router/router.go#L84)、[`distribution_service.go`](../backend/internal/service/distribution_service.go#L23)、[`ota_auth.go`](../backend/internal/middleware/ota_auth.go#L68)、[`channel_service.go`](../backend/internal/service/channel_service.go#L134)。

修复目标：能力判断 fail-closed；所有入口在路由和事务内都校验当前能力与租户状态；旧租户通过显式迁移得到能力，不能永久保留“缺记录即允许”的兼容逻辑。

### P0-4 供应商没有真正掌握产品授权和报价

供应商当前只能把商品设置为全局 `is_distributable`。关系激活后，分销商可以读取该供应商全部可分销商品，并自行调用导入创建状态为 `active` 的 `ProductOffer`，结算价直接取当前商品字段。`AllowedChannels` 也未在下单中执行。

这与目标中的“供应商决定哪个产品、哪个版本、以什么价格和配额授权给哪个分销商”相反。

证据：[`distribution_service.go`](../backend/internal/service/distribution_service.go#L131)、[`distribution_service.go`](../backend/internal/service/distribution_service.go#L141)、[`distribution_offer.go`](../backend/internal/model/distribution_offer.go#L8)。

修复目标：报价只能由供应商创建/审批并绑定产品版本、销售期、结算价、最低售价、渠道范围和配额；分销商只能接受并创建自己的展示 listing，不能制造供应商报价事实。

### P0-5 现金退款未原子恢复库存和分销资金

现金退款会写退款单、修改票、支付和订单状态，但不会执行取消路径中的库存回补和分销账户释放。分销商账户可能继续被扣款，有限库存也会永久减少。部分退款还缺少按履约项分摊的供应商退款事实。

证据：[`refund_service.go`](../backend/internal/service/refund_service.go#L114)、[`order_service.go`](../backend/internal/service/order_service.go#L647)。

修复目标：退款申请、规则审核、第三方退款、票权益作废、库存回补、分销资金/授信释放、供应商应收冲减和渠道回调应由一个可重试状态机协调；每一步幂等并可对账。

### P0-6 结算事实可重复、可单方伪造且退款分摊错误

供应商或分销商任一方都可提交自选佣金率生成结算单；查询不排除已进入其他结算单的履约单，也不更新履约结算状态。任一方可从任意状态直接标记 `paid`。

退款按销售主单聚合后，从每一个履约单都扣除一次。多供应商、多景区或零售价高于结算价时，会重复冲减或产生负数应收。

证据：[`settlement_controller.go`](../backend/internal/api/settlement_controller.go#L25)、[`settlement_service.go`](../backend/internal/service/settlement_service.go#L27)、[`settlement_service.go`](../backend/internal/service/settlement_service.go#L38)、[`settlement_service.go`](../backend/internal/service/settlement_service.go#L90)、[`settlement.go`](../backend/internal/model/settlement.go#L22)。

修复目标：佣金与账期来自合同/报价快照；履约结算行只能进入一个有效结算周期；退款按订单项/票权益和履约单归属分摊；确认、争议、付款、核销付款必须有角色分工、前置状态、付款凭证和审计。

### P0-7 历史迁移会固化旧漏洞并低算供应商应收

旧分销商品中的 `SettlementPrice` 曾是可由分销商修改的展示字段，当前迁移却直接把它升级为服务端权威 `ProductOffer` 结算价。历史零价或异常价会被合法化。

旧订单履约迁移按“销售单 + 供应商 + 景区”复用履约单，但只有第一个订单项写入结算金额，后续同组订单项不会累加，导致供应商应收少算。

证据：[`migrations.go`](../backend/internal/model/migrations.go#L237)、[`migrations.go`](../backend/internal/model/migrations.go#L279)。

修复目标：建立真实旧库 fixture；迁移前输出异常价、零景区、孤儿引用和账本差异清单；价格必须以供应商确认或可信来源重建；迁移后校验订单、库存、资金、履约和票权益守恒，失败时整批回滚。

### P0-8 团队入园绕过供应商票务履约

> **后续状态（2026-08-01）**：已修复并通过迁移、团队域、全量及竞态测试。旅行社只维护团队计划和名单；供应商操作员必须使用本租户、本景区的在线设备和检票点执行入园。系统逐成员校验团队已支付订单中的供应商票权益，写入 `CheckInRecord`、消费票和权益，并用幂等批次累计完成状态。无关租户不能读取团队名单、确认单、变更或入园批次。

旅行社租户可对自己创建的团队直接调用 `EnterBatch`。接口不要求团队已关联且已支付的销售订单，不要求票权益、有效合同、游玩日期或检票点；`device_id=0` 时直接允许。它只修改团队名单状态，不产生正式 `CheckInRecord`。

此外，团队完成状态用“本批入园人数”比较总人数，多批入园通常无法正确完成。

证据：[`team_service.go`](../backend/internal/service/team_service.go#L198)、[`team_service.go`](../backend/internal/service/team_service.go#L232)。

修复目标：旅行社维护计划和名单，供应商或其认证设备执行入园；每个入园成员必须关联有效票权益或明确的供应商人工放行审批，并进入统一核销事实与审计。

### P0-9 平台身份与默认租户管理员复用启动凭据

首次启动使用同一组 `Bootstrap.AdminUsername/AdminPassword` 创建默认租户 `super_admin` 和平台 `platform_admin`。逻辑上虽然分表，但泄露租户管理员口令即可尝试登录平台入口，最高权限安全边界没有真正分离。

证据：[`main.go`](../backend/cmd/main.go#L206)。

修复目标：平台根账号使用独立的一次性初始化流程和独立凭据；首次登录强制改密；平台高危操作支持二次认证、双人复核和完整审计。

### P0-10 金额与账本仍不满足整数分和守恒要求

`moneyCents` 先四舍五入到浮点两位，再乘 100 后直接转 `int64`。二进制浮点误差会把例如 0.29 转为 28 分；微信请求金额也使用直接截断。

分销下单已经区分现金和授信占用，但账本预占仍把总成本作为一个现金负数，取消时又只记录返还现金部分。全授信订单的账本无法重建账户状态。

证据：[`ledger_service.go`](../backend/internal/service/ledger_service.go#L12)、[`payment_service.go`](../backend/internal/service/payment_service.go#L190)、[`order_service.go`](../backend/internal/service/order_service.go#L452)、[`order_service.go`](../backend/internal/service/order_service.go#L482)。

修复目标：领域入口尽快改用整数分或十进制定点数；账本分别记录现金、授信、冻结、确认、释放和结算，不依赖可变余额字段解释历史。

## 5. 高优先级偏差与未完成闭环

### P1-1 产品版本只在首次下单时补建

商品更新直接覆写商品和票规，没有新建 `ProductRevision` 或失效旧版本；之后下单只要存在 `CurrentRevisionID` 就复用旧版本。新订单会引用旧 revision ID，却使用新的当前价格和规则生成票快照。

证据：[`product_service.go`](../backend/internal/service/product_service.go#L53)、[`order_service.go`](../backend/internal/service/order_service.go#L198)。

验收要求：每次影响销售或履约的修改产生不可变新版本；报价绑定明确版本；旧订单、票和结算始终可追溯到销售时版本。

### P1-2 新渠道接入层尚不能形成可靠订单

- 控制器把渠道账号 `code` 写入 `Order.Channel`，订单服务只接受 `online/ota/window`，常规 `ctrip/meituan` 代码会直接失败。
- 渠道代码只要求租户内唯一，认证却按代码全局查第一条，存在身份歧义。
- 直接提交本地 `product_id` 可绕过商品映射。
- 相同 `external_no` 的重试不比较产品、数量、日期和联系人，可能静默返回旧订单。
- `ChannelRequest` 只保存正文哈希；相同 request ID 和正文会重新执行处理器，未持久化并重放原响应。
- `PermissionsJSON`、`RateLimitPerMin`、IP 白名单和允许渠道均未执行。

证据：[`ota_controller.go`](../backend/internal/api/ota_controller.go#L102)、[`order_service.go`](../backend/internal/service/order_service.go#L319)、[`channel.go`](../backend/internal/model/channel.go#L8)、[`channel_service.go`](../backend/internal/service/channel_service.go#L134)、[`channel_auth.go`](../backend/internal/middleware/channel_auth.go#L70)。

### P1-3 平台治理写入与审计不是一个事务

租户状态/能力先提交，再另起事务记录审计。审计失败时接口报告失败，但治理变更已经生效。租户删除只检查订单、产品、用户和员工，遗漏景区、设备、票、履约、分销、资金、结算、团队、渠道及审计数据。

证据：[`tenant_controller.go`](../backend/internal/api/tenant_controller.go#L54)、[`tenant_service.go`](../backend/internal/service/tenant_service.go#L158)。

### P1-4 数据库无法证明关键关系同租户、同景区

SQLite 已启用外键，但关键所有权字段多数只有普通索引，没有复合候选键和复合外键。服务层若遗漏一次校验，数据库仍可保存“资源属于 A、TenantID 写成 B”或票、设备、履约景区不一致的数据。

证据：[`models.go`](../backend/internal/model/models.go#L52)、[`models.go`](../backend/internal/model/models.go#L202)、[`fulfillment.go`](../backend/internal/model/fulfillment.go#L5)、[`settlement.go`](../backend/internal/model/settlement.go#L5)。

### P1-5 数字退款只有任务，没有执行器

数字退款只创建 `pending` 退款和 `DigitalRefundTask`，主程序没有消费、调用第三方退款、退避重试或最终对账的 worker。这种实现没有伪造成功，方向是正确的，但只能称为“申请持久化”，不能称为退款闭环。

证据：[`refund_service.go`](../backend/internal/service/refund_service.go#L152)、[`main.go`](../backend/cmd/main.go#L139)。

### P1-6 POS 打印和交班不满足现场财务要求

- 打印桥返回失败时，收银页不检查结果，仍清空购物车和当前订单；持久化打印任务接口未接入。
- 交班应收按租户汇总开班后的全部现金支付，不限定设备、操作员或班次，也不扣现金退款。多个窗口会重复统计彼此现金。
- 班次只从 `localStorage` 恢复，缓存丢失后无法找回服务端开放班次。
- 售票不强制开班，也没有钱箱、备用金和操作员归属进入支付事实。

证据：[`SalesView.vue`](../desktop/src/renderer/src/views/SalesView.vue#L438)、[`SalesView.vue`](../desktop/src/renderer/src/views/SalesView.vue#L592)、[`operations_service.go`](../backend/internal/service/operations_service.go#L43)。

### P1-7 平台和三类租户还没有可运营工作台

- 管理端只有租户登录，未调用已有的 `/auth/platform/login`。
- 路由守卫只检查 token，不执行 `meta.role`；菜单不按能力和岗位过滤。
- 景区、渠道、团队、结算、总账、班次、打印任务和告警等后端能力基本没有对应页面。
- 租户页没有冻结、能力审批和审计操作，却展示后端永远不会返回的 `secret_key`。
- 用户页提供 `sub_admin/finance`，后端只接受 `admin`，创建必然失败。
- 分销页同时向所有租户展示供应商和分销商操作。

证据：[`LoginView.vue`](../admin/src/views/LoginView.vue#L42)、[`router/index.ts`](../admin/src/router/index.ts#L117)、[`App.vue`](../admin/src/App.vue#L31)、[`TenantView.vue`](../admin/src/views/TenantView.vue#L18)、[`UserView.vue`](../admin/src/views/UserView.vue#L45)。

### P1-8 平台全局治理和岗位资源范围尚未建成

平台 API 目前主要管理租户档案、状态和能力，不能全局监控订单、库存、设备、资金、支付不明、结算和异常，也没有受审计的限时代管流程。

租户员工只有逗号分隔角色和 `TenantID`。当一个供应商经营多个景区时，售票员、检票员和财务人员无法限定到指定景区、检票点、渠道或资金账户。

证据：[`router.go`](../backend/internal/router/router.go#L28)、[`models.go`](../backend/internal/model/models.go#L41)。

### P1-9 报表仍有事实口径不一致

商品排行把退款订单包含在销量和销售额中，但不减退款数量或金额。POS 交班同样不扣现金退款。报表尚未系统地区分销售日、支付日、游玩日、核销日和结算日。

证据：[`report_service.go`](../backend/internal/service/report_service.go#L74)、[`operations_service.go`](../backend/internal/service/operations_service.go#L55)。

## 11. 阶段判断

当前项目并非方向完全错误，而是“领域名词和表结构已经向目标靠拢，强制规则和运营闭环没有同步完成”。这类阶段最容易继续堆叠页面和接口，最后把错误事实固化得更深。

后续开发应遵守以下判定：

- 表或字段存在，不等于能力完成。
- API 返回成功，不等于跨角色闭环完成。
- 单元测试绿色，不等于未覆盖的领域不变量成立。
- 前端隐藏菜单，不等于后端授权。
- 兼容零值或旧字段，不得成为永久的授权绕过。
- 只有迁移、负向测试、异常恢复、操作界面和现场验收同时完成，才能把相应阶段标记为完成。

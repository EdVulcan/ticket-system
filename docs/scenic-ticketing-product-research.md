# 景区票务经营系统产品研究与当前项目差距

- 报告日期：2026-07-31
- 代码基线：`0b3f7c4`（分支 `codex/embedded-sqlite-hardening`）
- 研究目标：设计一套比通用平台更适合本景区日常经营的系统，而不是复刻智游宝。

## 1. 结论

当前项目已经证明了核心技术路线可行：单服务部署、SQLite、自动备份、多租户、商品、订单、支付、票码、核销、设备鉴权、基础 OTA API、分销关系和基础报表都已具备。

但它目前仍是“票务核心原型”，不是可以直接替换景区生产系统的完整产品。真正的差距不在页面数量，也不在是否复制智游宝菜单，而在以下四条业务链尚未形成完整闭环：

1. **窗口售票闭环**：开班 -> 售票 -> 收款 -> 打印/发码 -> 改签退票 -> 交接班 -> 日结对账。
2. **入园核销闭环**：票/证/码 -> 检票规则 -> 闸机或手持机 -> 离线降级 -> 异常处置 -> 客流统计。
3. **线上渠道闭环**：库存与价格发布 -> 预占 -> 下单 -> 支付确认 -> 发凭证 -> 核销/退票回传 -> 对账结算。
4. **旅行社团队闭环**：合作协议 -> 团队计划 -> 名单与人数变更 -> 团队取票/分批入园 -> 挂账或预付款 -> 结算。

建议把产品定位为：

> **景区自有的票务经营中台**。统一管理商品、价格、库存、订单、游客权益、核销、渠道和结算；窗口、闸机、OTA、旅行社只是不同业务入口，共用一套可信数据和状态规则。

首要目标不是“功能比智游宝多”，而是做到：

- 常用操作更少步骤，窗口与检票人员不必理解平台内部概念。
- 一个订单在售票、支付、发码、核销、售后、结算各环节都能追踪。
- 异常优先展示，超时订单、支付差异、失败回调、库存不一致能主动进入待办。
- 景区掌握自己的订单、游客、渠道和财务数据，不依赖外部平台才能查清业务。
- 保持单体部署和低运维成本，同时为闸机高峰、渠道重试和后续数据库升级保留边界。

## 2. 证据边界与研究方法

本报告用三种标识区分结论来源：

- **[公开事实]**：来自厂商官网、开放平台或政府采购公告，附公开链接。
- **[代码事实]**：来自当前仓库代码，只描述已经存在的模型和行为。
- **[产品建议]**：根据景区业务闭环做出的设计判断，需要结合本景区现场流程确认。

需要特别说明：

- 《智游宝平台发码验码接口开发指南（分时）》只是一个渠道发码、验码和售后接口文档，不是智游宝产品全量说明。
- 智游宝官网公开定位很宽，覆盖政府、旅游局、景区、酒店、客栈、旅行社和线上线下 O2O。它可以证明智游宝是综合平台，但不能证明某个具体景区购买或使用了其全部模块。
- 厂商产品页适合观察行业模块和术语，不等于每项能力都已在任意客户现场落地。
- 政府采购案例反映的是一个真实景区项目的建设范围，不应直接照抄为本景区需求。

## 3. 公开资料说明了什么

### 3.1 智游宝是行业样本，不是需求清单

**[公开事实]** 智游宝官网将自身描述为“智慧旅游公众服务支撑平台”，服务对象包含地方政府、旅游局、旅游景区、酒店、客栈和旅行社，并提供线上线下 O2O 技术支撑；官网还单独提供设备展示、解决方案和渠道合作入口。

这说明智游宝的边界远大于本地 DOCX 中的发码验码接口。反过来，这也说明不应把“复制智游宝”作为产品目标：综合平台为大量客户保留的复杂度，未必适合本景区的一线操作。

### 3.2 现场售检票必须同时考虑软件、票证和设备

**[公开事实]** 中国政府采购网公布的“恒山景区票务系统升级改造项目”包含自动售取票机、窗口身份证阅读器、护照/港澳台证件阅读器、扫码器、门票打印机、手持验票机、三辊闸、摆闸、人脸机、IC 卡和控制器。搜索索引中的采购内容还明确出现纸质票、身份证、二维码、人证比对、旅行社购票，以及散客票和团队票。

这证明完整票务系统不是一个后台订单表，而是售票终端、票证介质、检票设备、身份核验和业务规则共同组成的现场系统。

### 3.3 OTA 直连的难点是可靠履约，不只是“有下单接口”

**[公开事实]** 携程景点玩乐开放平台的标准订单接口包含预下单、订单创建、确认、核销、取消和凭证获取。官方文档建议采用预下单锁库存，并明确要求幂等、超时补偿、沙箱自测、签名、防篡改和 AES 加密。文档还区分“订单取消”和“仅退款”。

因此，一个可以投入生产的 OTA 接入至少需要：库存预占、支付确认、查单补偿、可靠回调、幂等、签名、沙箱、错误码和售后语义。当前项目只有“商品列表、已支付下单、取消、查询”的基础骨架。

### 3.4 旅行社团队业务必须独立建模

**[公开事实]** 成熟景区票务厂商公开的旅行社/团队模块通常独立管理团队、导游、团单和团队财务，并支持为不同团队配置可售产品、协议价、支付方式、打印单据、结算和经营报表。

这与普通 OTA 订单不同。团队业务包含合作关系、人员角色、行程变更、授信和周期结算，不能仅在普通订单上增加一个 `groupNo` 字段。

## 4. 面向本景区的完整业务能力模型

以下内容是目标产品能力模型，不代表必须一次性全部开发。

### 4.1 产品、票规、价格与库存

**[产品建议]** 所有销售入口应共用一套产品中心：

- 景区、园区、游玩项目、检票点和营业日历。
- 单票、套票、联票、年卡、预约票、团队票、免票和司陪票。
- 成人、儿童、老人、学生、本地居民等人群规则。
- 原价、窗口价、渠道价、协议价、结算价和佣金规则。
- 固定日期、有效期、指定场次、入园时间段和最晚预订时间。
- 总库存、日期库存、时段库存、渠道配额、预占库存和安全库存。
- 一次入园、多次入园、多园区联票、M 选 N 权益和部分核销规则。
- 退票、改期、过期、实名、限购和黑名单规则。

核心原则是：商品是销售描述，票是游客权益，库存是可售容量，三者不能混为同一个状态。

### 4.2 线下窗口售票

**[产品建议]** 窗口端应按收银员实际工作顺序设计：

- 开班、备用金、钱箱和设备自检。
- 快速选票、人数调整、优惠资格和实名读取。
- 现金、微信、支付宝、银行卡、组合支付和挂账。
- 纸票、二维码票、身份证票、IC 卡票的发放与补打。
- 未支付关闭、支付结果不明查单、误售作废、改期和退票。
- 原订单补票、部分退票和异常票人工处理。
- 交接班、现金盘点、支付渠道汇总、差异说明和日结锁定。
- 售票员、审核员、财务员权限分离和完整操作审计。

界面上应优先展示票种、日期/场次、数量、应收、实收和出票结果，不把复杂后台字段暴露给售票员。

### 4.3 验票、闸机与现场处置

**[产品建议]** 入园系统至少应覆盖：

- 闸机、手持机和人工工作台使用同一核销服务。
- 二维码、纸票条码、身份证、护照/港澳台证件、IC 卡；人脸仅在业务确有需要且合规时接入。
- 重复票、退票、过期票、未到日期、错误检票点、次数耗尽和黑名单的明确提示。
- 团队整团核销、分批入园、导游带团和临时加人。
- 设备注册、密钥轮换、心跳、远程停用、固件/协议版本和操作审计。
- 断网时的离线票包或本地边缘缓存，以及恢复后的去重同步。
- 实时入园人数、时段峰值、各入口流量、在园人数和异常拒绝统计。

核销必须幂等。设备重复提交同一请求时，不得重复消耗游客权益。

### 4.4 线上渠道和 OTA

**[产品建议]** 渠道接入层不应把携程、美团、抖音或智游宝协议直接写进订单核心，而应采用“统一渠道订单 + 渠道适配器”：

- 渠道、门店、应用、密钥、IP 白名单、版本和回调地址管理。
- 本地产品与渠道商品/规格映射。
- 价格、日期、场次库存、渠道配额和停售同步。
- 订单验证、预下单锁库存、支付确认、取消预占和超时关闭。
- 外部主订单、子订单、游客、凭证和本地订单的稳定映射。
- 幂等键、请求日志、标准错误码、限流和防重放。
- 下单超时后主动查单，避免“不确定状态”直接退款或重复出票。
- 发码、核销、改期、退票和退款结果的可靠回调。
- 持久化事件队列、失败重试、人工重放和送达记录。
- 渠道账单导入、订单/支付/退款/核销多方对账和差异处置。
- 沙箱、联调工具、签名示例和接口监控。

### 4.5 旅行社团队业务

**[产品建议]** 团队业务建议形成独立模块，并与统一订单、库存和票权益连接：

- 旅行社、分社/门店、业务员、导游、领队、司机档案。
- 组团社、地接社、景区三方关系和责任归属。
- 合同、协议价、阶梯价、底价、返佣、有效期和适用产品。
- 团队计划、团号、行程、到园日期、时段、集合点和联系人。
- 预报人数、最终人数、名单 Excel 导入、重复证件校验和增减员。
- 成人、儿童、老人、免票、导游票、司陪票等人数结构。
- 导游证、车牌、车辆、司机和备注附件。
- 预付款、余额、授信额度、挂账、担保、月结和逾期控制。
- 团队确认单、取票单、分批入园、整团码或个人票码。
- 临时加人、成员替换、退团、部分退票、改期和异常审批。
- 团队结算单、返佣、发票状态、应收账龄和对账确认。

“团队计划”和“财务结算”应独立于普通售票订单。一个团队可能多次增补、分批支付、分批出票和分批入园，而最终合并结算。

### 4.6 售后与异常工作台

**[产品建议]** 售后不是把订单状态改成 `refunded`，而是一套可审计流程：

- 按整单、订单项、单张票、人数或证件部分退票。
- 退票申请、规则计算、人工审核、支付退款、库存回补和渠道回调。
- 改期时原库存释放和新库存占用必须原子化。
- 支付成功但订单失败、订单成功但发码失败、渠道超时、重复扣款等异常自动建待办。
- 每个异常显示来源、当前状态、推荐动作、处理人、处理时限和完整日志。

### 4.7 财务、对账与经营分析

**[产品建议]** 财务域至少需要：

- 窗口班次和日结、支付渠道日账单、退款流水和现金差异。
- 渠道预存款、授信、冻结、消费、退款、佣金和账期。
- 旅行社应收、预付款、挂账、月结和逾期账龄。
- 订单、支付、退款、核销和渠道账单的自动勾兑。
- 销售额、实收、退款、核销收入、未消费票、渠道成本和毛利口径。
- 按日期、产品、渠道、窗口、售票员、旅行社和导游分析。

报表必须说明统计口径。销售日期、游玩日期、核销日期和结算日期不能混用。

### 4.8 权限、安全与连续经营

**[产品建议]** 景区系统保存证件、手机号、票码和支付信息，需要：

- 按岗位授权，敏感操作二次确认，退款和授信调整可配置审批。
- 证件号、手机号、票码加密存储或脱敏展示，访问留痕。
- 操作日志、接口日志和设备日志可关联到订单，但敏感报文需脱敏。
- 自动备份、恢复演练、数据导出、监控告警和容量预警。
- 断网、渠道故障、支付故障、闸机故障的明确降级预案。
- 数据保留期限、离职账号停用和密钥轮换机制。

## 5. 当前项目覆盖与差距

| 业务域 | 当前代码已经具备 | 主要缺口 | 判断 |
|---|---|---|---|
| 产品与票规 | 商品、有效期、实名开关、限购字段、退票规则字段、总/日库存、时段配置 | 时段配置未进入下单扣减；套票/联票/多权益模型不足；价格计划与渠道配额缺失 | 部分覆盖 |
| 统一订单 | 订单、订单项、票、外部单号幂等、分页搜索 | 缺少预占订单、游客逐人信息、订单事件、改期和复杂状态机 | 部分覆盖 |
| 窗口售票 | 线下商品、窗口订单、现金/微信/支付宝支付 | 缺少班次、钱箱、组合支付、打印、补打、作废、交接班和日结 | 原型级 |
| 票与核销 | 票码、检票点、核销次数、成功/拒绝记录 | 缺少身份证/IC 卡等介质映射、离线核销、团队核销和可配置联票权益 | 部分覆盖 |
| 设备 | 设备注册鉴权、心跳、检票接口、闸机模拟器 | 缺少真实厂商协议适配、离线策略、密钥轮换、设备告警和远程运维 | 原型级 |
| OTA | 签名、防重放、商品列表、下单、取消、查询 | 缺少预下单、支付确认、库存查询、凭证、部分退票、回调、补偿、沙箱和对账 | 基础骨架 |
| 分销 | 合作申请、审核、产品导入、预存款/授信消费与回补 | 当前是租户间商品复制和资金账户，不是旅行社团队业务 | 基础骨架 |
| 旅行社团队 | 无独立团队模型 | 缺少旅行社/导游/团号/名单/车辆/协议价/团单/结算全链路 | 未覆盖 |
| 售后 | 产品存在退票规则字段，订单状态预留退款状态 | 没有退票申请、审核、部分退、支付退款和回调闭环 | 未覆盖 |
| 财务与报表 | 分销资金流水、销售/产品/渠道基础报表 | 缺少窗口日结、支付对账、渠道结算、团队应收和统一财务口径 | 部分覆盖 |
| 部署与备份 | 单服务、SQLite WAL、串行写入协调、自动备份和保留策略 | 需要恢复演练、峰值容量测试、离线边缘策略和生产监控 | 路线可用 |

主要代码依据：

- `backend/internal/model/models.go`：商品、订单、订单项、票、核销记录和日期库存。
- `backend/internal/service/order_service.go`：订单创建、日期库存原子扣减、分销资金扣减和票码生成。
- `backend/internal/api/ota_controller.go`：当前四个 OTA 接口的实际边界。
- `backend/internal/middleware/ota_auth.go`：签名、时间窗和防重放。
- `backend/internal/router/router.go`：窗口、核销、分销、OTA、支付和报表入口。
- `backend/internal/backup/backup.go`：SQLite 在线备份与保留策略。

其中有两个容易被界面误导的地方：

1. `time_slot_config` 当前只是商品配置 JSON；库存扣减只实现了总库存和“商品 + 日期”库存，尚未按时段扣减。
2. `Ticket` 虽然有游客姓名、电话和证件字段，但创建订单时只把联系人写入票，尚未实现每位游客逐人采集和证件绑定。

## 6. 比通用平台更适合本景区的设计原则

### 6.1 按工作任务设计，不按技术模块设计

售票员看到“开班、售票、补打、退票、交班”；检票员看到“验票、异常放行、设备状态”；渠道运营看到“商品映射、库存、失败订单、回调”；旅行社经理看到“团队计划、到园、结算”。不要让所有岗位面对同一套复杂菜单。

### 6.2 一张订单详情解释清全部实际情况

订单页应同时展示：来源渠道、外部单号、游客、票、支付、退款、核销、渠道消息、财务结算和操作时间线。用户不应在多个页面手工拼接真相。

### 6.3 正常流程尽量自动，后台重点处理异常

正常 OTA 订单自动完成预占、确认、发码和回传；运营台只聚合库存冲突、支付不明、发码失败、回调失败、退款失败和对账差异。

### 6.4 保持模块化单体，不提前引入微服务

当前“一个程序 + SQLite + 自动备份”符合低运维目标。后续应先通过清晰模块边界、持久化任务表、设备离线缓存和压力测试解决问题，而不是为了架构形式增加 Redis、消息队列和多服务。

当实测峰值超过单机 SQLite 写入能力、需要多实例容灾或跨园区集中部署时，再把数据库替换为 PostgreSQL。订单、库存、核销和事件模块应通过仓储/事务边界隔离，避免迁移时重写业务。

### 6.5 外部协议可插拔，内部状态保持统一

智游宝、携程、美团、抖音和旅行社自有系统都应通过适配器转换为内部标准命令和事件。渠道字段不能反向污染核心订单模型。

## 7. 建议的实施阶段

以下是产品边界建议，不是本轮开发任务。

### 第一阶段：可承担景区日常生产

目标是让“窗口散客 + 现场核销 + 一个主要 OTA + 基础团队”跑通：

1. 统一订单、支付、票权益、库存预占、取消、改期和退款状态机。
2. 真正的日期/时段库存，以及并发下单和回补一致性。
3. 窗口开班、售票、支付、打印/发码、退票、交班和日结。
4. 闸机/手持机统一核销、设备管理、幂等和基础断网方案。
5. 一个生产级 OTA 适配器，覆盖预下单、确认、查单、凭证、取消、退票和回调。
6. 旅行社档案、协议价、团队计划、人数变更、团队取票和基础结算。
7. 异常工作台、操作审计、备份恢复演练和关键监控。

验收应使用完整业务链，而不是单接口成功：

- 窗口开班 -> 售票 -> 收款 -> 出票 -> 核销 -> 退一张票 -> 交班 -> 日结。
- OTA 预下单 -> 支付确认 -> 发凭证 -> 核销 -> 回调；任一步骤超时后可自动查单和补偿。
- 旅行社建团 -> 导入名单 -> 临时增减员 -> 分批入园 -> 生成结算单。

### 第二阶段：规模化渠道和精细运营

- 增加多个 OTA 和智游宝适配器，建设渠道联调与监控中心。
- 完善部分退票、审批、退款、回调、自动对账和差异处理。
- 完善旅行社授信、月结、返佣、应收账龄和多方确认。
- 增加实时客流、在园人数、核销率、未使用票和渠道毛利分析。
- 完善实名、证件加密、权限、数据留存和多园区能力。

### 第三阶段：只做已被经营验证的扩展

会员、营销裂变、导游返佣、年卡、人脸、停车、餐饮零售、酒店套票、多商户分账和动态定价都可以扩展，但应以本景区真实收入或效率收益为前提，不因为竞品存在就进入范围。

## 8. 开发前必须完成的现场盘点

要做到“更适合本景区”，下一轮讨论应先取得以下真实数据：

1. 售票窗口数量、班次、售票员人数、现金比例和当前交接班流程。
2. 闸机、手持机、身份证阅读器、打印机的品牌、协议、数量和网络拓扑。
3. 平日/周末/节假日峰值：每分钟售票数、下单数和检票数。
4. 现有票种、价格、人群、有效期、入园次数、联票和退改规则。
5. 已接 OTA、智游宝在链路中的角色、外部商品编码和对账方式。
6. 旅行社数量、合同价规则、团队预报方式、名单要求、导游/车辆管理和结算周期。
7. 是否强实名，需支持哪些证件，是否有本地居民、学生等资格核验。
8. 断网时允许继续售票或放行的风险边界，以及最长可接受中断时间。
9. 财务目前如何确认现金、微信/支付宝、OTA、旅行社挂账和退款。
10. 哪些现有智游宝操作最费时、最容易出错、最希望取消。

这份盘点比继续收集竞品菜单更重要。它将决定第一阶段的数据模型、设备边界和验收指标。

## 9. 本地接口文档的正确用途

《智游宝平台发码验码接口开发指南（分时）》应保留为“智游宝渠道适配器”的参考资料，主要覆盖：

- 分时库存查询。
- 已支付/未支付订单创建、支付确认和取消。
- 订单、检票状态和核销明细查询。
- 票码图片、二维码长短链接和短信交付。
- 部分退票、退票审核和退票结果查询。
- 订单完结、核销、退票、到付确认/取消等回调。
- 到付订单查询。

它不应用来定义内部订单模型，也不应用来推断智游宝完整产品范围。未来对接时，应把这些 XML 协议转换为本系统统一的库存、订单、票、退款和事件模型。

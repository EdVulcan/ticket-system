# 现场联调准备清单

本文只记录本地代码无法替代的真实条件。取得对应设备、协议、凭据或业务样本后，
再按本清单继续开发和验收。未取得条件前，相关接口必须明确失败或保持待确认，
不得用模拟成功作为生产完成。

## 1. 支付商户

需要准备：

- 微信支付商户号、应用 ID、API v3 密钥、商户私钥与证书序列号、平台公钥/证书、可公网访问的通知地址。
- 支付宝应用 ID、应用私钥、支付宝公钥、网关和通知地址。
- 一台可出示真实付款码的测试手机，以及可退款的测试资金。

需要验收：主扫支付、支付宝付款码、微信付款码、超时查单、迟到回调、重复回调、
进程重启恢复、全额/部分/组合支付退款、换票补差与退差价、日终支付对账。
微信付款码适配器在取得商户协议并完成测试前保持关闭。

## 2. 窗口设备

每类设备至少提供一台实物及以下信息：品牌、型号、连接方式、驱动或 SDK、协议文档、
示例程序、纸张/卡片规格、Windows 版本和位数。

- 小票或票卡打印机：打印、缺纸、断线、卡纸、重打及切纸。
- 身份证阅读器：读取、取消、超时、重复刷证和敏感数据保留规则。
- 扫码枪：二维码和付款码输入方式，是否模拟键盘，结束符配置。
- 钱箱（若使用）：开箱指令和权限要求。

需要在景区低配置窗口电脑上测量冷启动、连续售票、打印恢复、内存占用和 8 小时运行。
当前 Wails 桥在适配器未配置时 fail-closed，并保留订单和打印任务供重打。

## 3. 检票设备与网络

需要准备闸机/手持机的品牌型号、厂商协议或 SDK、设备认证方式、开闸指令、返回码、
心跳周期、离线缓存能力、固件版本，以及景区检票点与局域网拓扑。

需要现场确定：断网时能否核销、离线票包范围、风险承担人、缓存时限、重传顺序、
人工放行权限和审计要求。验收必须覆盖重复扫码、并发扫码、跨景区票、已退款票、
过期票、设备断线重传和服务重启；A 景区门票在 B 景区始终不得核销。

## 4. 下游销售渠道

当前只考虑携程、美团等真实下游销售渠道；智游宝不作为下游。每个厂商需要提供：

- 最新接口协议、签名规则、错误码、沙箱/测试账号、IP 白名单要求。
- 商品、库存、预占、确认、查单、取消、退款、凭证和回调协议。
- 回调重试规则、超时判定、人工重放限制和账单样本。

取得资料后再实现厂商适配器、退款和回调投递。内部渠道账号、权限、限流、商品映射、
请求恢复、渠道订单综合查询和账单差异下钻已可复用，不为单个厂商另建订单模型。

## 5. 数据恢复演练与可选旧库导入

新系统不以迁移任何旧系统数据为交付前提。只有以后明确提出旧库导入需求时，才需要提供
脱敏后的真实 SQLite 样本和对应应用版本，并把导入作为单独的审计、转换与验收项目；
不在原库直接试验，也不猜测修复零景区、跨租户归属、异常价格或孤儿引用。

PostgreSQL 自定义格式备份、密钥配套备份、恢复校验和回滚 dump 已有真实集成测试。
取得实际部署目录后，还需执行一次“停服务 -> 备份 -> 恢复到副本 -> 启动校验 -> 回滚”
的人工演练并记录耗时。

## 6. 业务样本与生产容量

需要景区提供：窗口交班样表、供应商/分销商月度账单、旅行社合同与团队确认单样式、
主要岗位和例外处理规则。只据此调整现有 CSV、确认单和页面，不建设通用 ERP、总账、
发票或模板设计器。

容量验收需要确认售票窗口数、闸机数、峰值每秒核销、峰值每分钟下单、日订单量、
数据保留年限和可接受恢复时间。使用计划部署电脑和真实网络做峰值、8 小时稳定运行、
备份期间写入和断电恢复测试。生产数据库已采用 PostgreSQL，不预先引入 Redis、消息队列
或多服务架构。

## 7. 当前可交付边界

本地可自动验证的业务逻辑、租户隔离、PostgreSQL 并发事务和备份恢复、管理端多角色访问、
窗口核心交互和渠道订单查询均已纳入测试。以下内容在对应真实条件到位前仍是生产阻断项：
真实数字支付、真实打印/读卡/扫码/闸机、真实渠道协议、实际部署目录恢复、
月度双方对账和目标机器容量/长稳验收。

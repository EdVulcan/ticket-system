# 现场联调准备清单

本文只记录本地代码无法替代的真实条件。取得对应设备、协议、凭据或业务样本后，
再按本清单继续开发和验收。未取得条件前，相关接口必须明确失败或保持待确认，
不得用模拟成功作为生产完成。

## 1. 支付商户

当前联调目标（2026-08-05）：窗口售票收款。现场已确认使用支付宝官方碰一下终端，支持扫描
顾客付款码和碰一下收款。支付订单、查单、退款和回调继续复用本系统支付宝交易事实；终端侧只增加
传递应收金额及接收付款凭证/结果的轻量桥接，不另建一套支付模型。仍需取得设备具体型号、连接方式、
设备设置页或接口/SDK 文档。现场所称“聚合支付”是分别配置微信、支付宝商户参数后，由售票系统在
统一收款入口按付款凭证自动识别渠道，并非另接第三方聚合收单网关；本系统继续采用相同交互模式。
窗口端另保留现金和备用 POS 机两种线下已收款登记。备用 POS 机不与本系统通信，由售票员确认外部设备支付成功后手工登记；其班次金额与现金分开汇总，不计入钱箱应交金额。

需要准备：

- 微信支付商户号、应用 ID、API v3 密钥、商户私钥与证书序列号、平台公钥/证书、可公网访问的通知地址。
- 支付宝应用 ID、应用私钥、支付宝公钥、网关和通知地址。
- 一台可出示真实付款码的测试手机，以及可退款的测试资金。

需要验收：主扫支付、支付宝付款码、微信付款码、超时查单、迟到回调、重复回调、
进程重启恢复、全额/部分/组合支付退款、换票补差与退差价、日终支付对账。
  微信付款码适配器已实现官方接口、主动查单和超时撤销；在 API v2 密钥、商户证书未齐全或真实小额联调未通过前，不应投入正式窗口收款。

  管理端“支付参数配置”会分别展示扫码、付款码、主动查单、原路退款和支付结果通知的配置状态。只有必要字段及租户专属 HTTPS 回调地址完整时才能启用渠道；“配置已就绪”仅代表本地参数完整，不代表真实商户联调已经通过。窗口端付款码入口会自动识别微信或支付宝，微信付款码在结果不明确时保持待确认并主动查单，超时后使用商户证书撤销，避免重复收款。

## 2. 窗口设备

每类设备至少提供一台实物及以下信息：品牌、型号、连接方式、驱动或 SDK、协议文档、
示例程序、纸张/卡片规格、Windows 版本和位数。

- 小票或票卡打印机：打印、缺纸、断线、卡纸、重打及切纸。系统当前由服务端按已发布的结构化打印模板生成 `PrintDocument` 快照，任务保存模板版本、内容哈希、纸张宽度和副本数；模板发布不会改写历史任务。混合票种订单按票生成任务，硬件桥不得接收客户端订单对象或任意脚本模板。
- 身份证阅读器：读取、取消、超时、重复刷证和敏感数据保留规则。
- 扫码枪：二维码和付款码输入方式，是否模拟键盘，结束符配置。
- 钱箱（若使用）：开箱指令和权限要求。

需要在景区低配置窗口电脑上测量冷启动、连续售票、打印恢复、内存占用和 8 小时运行。
当前 Wails 桥在适配器未配置时 fail-closed，并保留订单和打印任务供重打；旧的整单调用若命中多个不同模板会被服务端拒绝，避免使用第一张票的版式误打其他票。

## 3. 检票设备与网络

云端直连接口和轻量 `gate-client` 已实现 HMAC 签名、时间窗、nonce 防重放、每设备限流、持久请求幂等、景区/检票点绑定校验、加密设备密钥、本机断线恢复状态，以及物理开闸结果回报。升级前已有设备需先轮换密钥；现场部署必须配置可持久写入的 `GATE_STATE_FILE`。部署与驱动边界见[闸机直连客户端部署说明](./direct-gate-client.md)。

需要准备闸机/手持机的品牌型号、厂商协议或 SDK、设备认证方式、开闸指令、返回码、
心跳周期、离线缓存能力、固件版本，以及景区检票点与局域网拓扑。

需要现场确定：断网时能否核销、离线票包范围、风险承担人、缓存时限、重传顺序、
人工放行权限和审计要求。验收必须覆盖重复扫码、并发扫码、跨景区票、已退款票、
过期票、设备断线重传和服务重启；A 景区门票在 B 景区始终不得核销。

当前只采用直连云端方式，不开发离线票包或本地核销网关。具体厂商开闸 SDK、串口/TCP 指令仍需取得实物和协议后接入；未配置真实驱动时客户端明确上报失败。

## 4. 下游销售渠道

当前只考虑携程、美团等真实下游销售渠道；智游宝不作为下游。每个厂商需要提供：

- 最新接口协议、签名规则、错误码、沙箱/测试账号、IP 白名单要求。
- 商品、库存、预占、确认、查单、取消、退款、凭证和回调协议。
- 回调重试规则、超时判定、人工重放限制和账单样本。

携程供应商预下单、支付同步确认、预下单取消、未核销整单取消、订单查询和核销通知已完成协议代码，
供应商沙箱订单 18 项遍历已全部通过；仍需根据合同确认部分退订和仅退款范围。
美团取得资料后再实现厂商适配器。内部渠道账号、权限、限流、商品映射、请求恢复、
渠道订单综合查询和账单差异下钻继续复用，不为单个厂商另建业务订单模型。

携程沙箱联调状态（2026-08-09）：价格单日期、价格多日期、库存单日期和库存多日期四项遍历
均已通过；订单测试产品和商品映射已配置。测试域名审核已通过，订单商家接口已从根域名修正为
`https://ymsq.edvulcan.top/api/v1/integrations/ctrip/order`。真实预下单请求已到达本系统，签名校验和 AES 解密均已通过，并进入业务参数校验。
真实报文确认 `CreatePreOrder` 不传订单项编号、`PayPreOrder` 才传正式 `itemId`，且两个服务会复用同一 `sequenceId`；系统已按该协议修正订单项回填和“账号 + 服务 + 流水号”幂等作用域（schema 76）。订单 18 项已全部通过，核销通知由服务器可靠投递并获得携程 `0000` 成功响应。生产凭据、网络来源和合同能力范围完成前，不标记为生产渠道可用。

非指定日期价库补充状态（2026-08-09）：代码和自动化已按 `DATE_NOT_REQUIRED` 生成无日期价格、库存报文；真实沙箱价格任务已返回 `0000`。同批库存任务因携程当时没有处于等待库存通知的用例而返回 `0011`，需要在携程页面单独开启对应库存用例后再发送一次，完成前不把非指定日期价库标记为全部通过。

## 5. 数据恢复演练

新系统不以迁移任何旧系统数据为交付前提，也不提供 SQLite 运行或导入路径。以后若单独立项
导入旧系统数据，应使用独立转换工具和脱敏样本，不把旧数据库驱动重新带回主应用。

PostgreSQL 自定义格式备份、密钥配套备份、恢复校验和回滚 dump 已有真实集成测试。
取得实际部署目录后，还需执行一次“停服务 -> 备份 -> 恢复到副本 -> 启动校验 -> 回滚”
的人工演练并记录耗时。

## 6. 业务样本与生产容量

需要景区提供：窗口交班样表、供应商/分销商月度账单、旅行社合同与团队确认单样式、
主要岗位和例外处理规则。只据此调整现有 CSV、确认单和页面，不建设通用 ERP、总账、
发票或模板设计器。

容量验收需要确认售票窗口数、闸机数、峰值每秒核销、峰值每分钟下单、日订单量、
数据保留年限和可接受恢复时间。使用计划部署电脑和真实网络做峰值、8 小时稳定运行、
备份期间写入和断电恢复测试。生产数据库已采用 PostgreSQL，不预先引入 Redis、消息队列
或多服务架构。

## 7. 当前可交付边界

本地可自动验证的业务逻辑、租户隔离、PostgreSQL 并发事务和备份恢复、管理端多角色访问、
窗口核心交互和渠道订单查询均已纳入测试。以下内容在对应真实条件到位前仍是生产阻断项：
真实数字支付、真实打印/读卡/扫码/闸机、真实渠道协议、实际部署目录恢复、
月度双方对账和目标机器容量/长稳验收。

# 小红书普通门票上线测试单

适用 AppID：`672997dc4889610001aa80b2`。首发范围为本系统自行出票的普通门票；酒店、预约、智游宝实际出票不在本次放行范围。业务依据为[开发基线](./platform-multitenancy-development-guide.md)与[现场验收要求](./field-integration-readiness-checklist.md)，代码修复及自动化证据见[本轮审计记录](./xiaohongshu-release-audit-2026-09-11.md)。

判定规则：**A1–A8 全部通过、实际启用功能对应的 B 项通过、C 发布前核对完成，才可以正式开放普通门票售卖。** 任何重复扣款、错误金额、跨景区核销、已退款票可用、已付款订单丢失均阻止上线。测试失败先记录订单号和时间，修复后重测相关路径，不直接在数据库修改状态来算通过。

本单初始所有人工验收项均为未完成；之前版本的成功反馈不能直接代替本次验收。GitHub 部署只更新后端和管理端，**不代表小红书原生小程序已上传、审核或发布**。

## 准备

1. 确认本轮 GitHub Actions 全部必要任务及 deploy 成功，正式 `/api/v1/ready` 的 revision 等于本次发布提交，schema 为 117。本轮无新增迁移，不回填旧订单。
2. 从本次提交的小程序工程重新编译、上传到上述正式 AppID，设置体验版。记录提交号、小程序版本和体验时间；测试人员通过真实小红书客户端进入，不能只用开发者工具。
3. 准备已审核通过、允许未使用退款的普通测试门票、真实检票点、游客账号、后台管理员。选择实际准备出售的票型；若销售多份票，使用支持一人一码的票种，整单一码仍限一份。
4. 使用可接受的小额真实交易；测试售价和退款政策由后台正常配置并完成必要审核。A3 核销单和 A5 退款单必须分开，不能为了测试退款假定已使用票仍可自助退。
5. 至少在实际目标 Android、iPhone 各完成一次登录、选购、支付和票码展示；其余深入测试可主要在一台手机完成。准备约 4–6 笔订单，具体以覆盖启用票型为准。

## A：普通门票必测

| 完成 | 编号 | 怎么测 | 通过标准 |
| --- | --- | --- | --- |
| [ ] | A1 入口与商品 | 全新进入体验版；浏览商城、商品、日期/数量、订单列表；退出重新进入。 | 正式商户名称、商城图与商品图正确；价格、日期、数量、退票规则一致，无测试域名或占位内容；登录授权可完成，拒绝授权有可理解的提示。固定价格不显示无意义的“起”。 |
| [ ] | A2 支付与出票 | 购买一张实际销售票，真实付款；返回订单页，退出小程序再回来；后台同时查渠道订单与“销售中心→线上订单”。销售多份时再覆盖一次两份订单。 | 实付金额与确认页一致；同一订单在两处后台均可查且能按小红书/状态等条件筛选；票数、使用日期、票名一致，二维码可读。平台支付成功但签发未完成时显示处理中，最终恢复出票，不要求重复支付。 |
| [ ] | A3 现场核销 | 用 A2 票在实际检票点扫码；核销成功后再次扫码。如果首发使用闸机，实际完成一次开闸通行；手机核销则验证手机端。 | 正确景区/检票点成功且扣次正确；一次性权利重复扫码拒绝，不能重复计收入。小程序显示已使用；游客不能自助退已使用票。闸机“接口成功”不能代替实际开闸。 |
| [ ] | A4 多点与拒绝 | 对首发多点票，在第一个点使用后重新打开电子票，再去第二个允许检票点；使用不允许检票点/其他景区验证拒绝。首发指定日期票还要用不在有效日期的测试票验证拒绝。 | 订单已完成也不隐藏尚需使用的二维码；每个检票点按售出规则独立扣次，剩余权利能使用；超范围、错误日期和超次数拒绝。仅首发无多点/指定日期票时，可把对应分支注明“不适用”。 |
| [ ] | A5 游客主动退款 | 新买未使用票，先保存票码截图；游客从电子票/订单页主动整单退票，在小程序和后台观察状态，并核对实际到账，再用旧截图扫码。 | 提交后明确显示退款处理中，期间票码暂停核销；最终原路到账金额等于实付，小程序和后台均更新为已退款；旧截图始终不能核销；重复点击不重复退款。不能把“申请成功”算成到账。 |
| [ ] | A6 后台退款与权限 | 再买一笔未使用订单，由授权管理员在后台正常办理整单退款；普通无权限员工查看相同入口。若正式销售不可退票，还要用其销售政策验证游客不能自动退、授权例外有明确确认与原因。 | 授权后台有可用处理入口，到账与状态一致，票失效且操作可追溯；无权限员工不能退款。不可退政策不会被任意管理员绕过。 |
| [ ] | A7 取消和断网恢复 | 下单后关闭支付窗口，再从订单列表继续支付；另建一笔订单不支付，等平台确认关闭。再做一次提交时断网/立即退出，恢复网络后回原订单核对。 | 关闭支付窗口不被当成已取消/已付款；继续支付使用原订单金额。平台确认关闭后才释放库存/资格。未知创建结果不允许把原请求改为别的日期/数量支付；恢复后不丢已付单、不重复扣款，订单金额和选择一致。精确“服务端已落单但响应丢失”由自动化故障注入补充，单次手动断网不等于覆盖该时序。 |
| [ ] | A8 账目与状态核对 | 将以上订单逐笔核对：小红书平台、游客实付/到账、渠道订单、线上订单、核销记录和销售报表；记录支付、到账、页面更新时刻。 | 金额按分一致，退款/核销不重复累计，原价与实付区分正确；没有已到账但长期未同步、支付成功又显示未付款、等待人工改库才能恢复的订单。仍在平台处理中的订单保持处理中，待最终结果确认后本项才通过。 |

退款状态同步要同时记录：平台退款结果、真实到账、小程序和后台更新时刻。收到平台最终结果后应自动推进，不能依赖反复提交退款。若持续停留旧状态，保留订单号核查回调与查询日志；不将支付机构到账耗时直接等同于系统刷新延迟。

## B：启用时追加的测试

### B1 随机立减活动

- [ ] 同游客刷新、退出重进、切换参与商品，不重新抽金额或延长有效期；非参与商品不享受也不消耗机会。
- [ ] 下单两份参与票，确认只对整单减一次；确认页、平台实付、每份票分摊之和、后台完全一致；整单退款按实际支付金额到账，不退原价。
- [ ] 机会过期未使用不能立刻重领；再次获得间隔按后台配置从获得时间计算。长间隔先验证“不重领”，跨天再次可领由自动化时间测试加后续实测记录覆盖，不要求等一个月才能首发。
- [ ] 未下单时关闭活动或移除该商品，提交时重新校验并展示最新应付金额；已提交订单仍按锁定金额支付。关闭支付窗口不释放，平台确认关闭后按原有效期处理；退款不重新赠送机会。

若未全部通过，关闭活动后仍可验收 A 项并上线普通原价售票。

### B2 误核销后例外退款

- [ ] 实际核销一笔普通团购券，由履约供应商初始管理员填写原因并进行整单退款；核对真实到账、原票失效、原核销记录留痕、有效核销收入冲销及结算不重复冲销。
- [ ] 游客、普通管理员、分销商和其他供应商均不能执行该例外。

未通过前不向运营开放使用该例外，保留普通未使用退款；此能力是受限权限路径，不假定存在独立功能开关。

### B3 官方分销/笔记与直播带货

- [ ] 平台分销商品配置可保存，真实笔记或直播商品入口能打开当前小程序的正确商品。
- [ ] 从该入口真实下单，平台能确认对应达人归因、计佣金额及订单状态；再完成一笔退款，平台佣金状态相应处理。
- [ ] 取得可查询的佣金/结算明细，金额与平台约定一致。若需等待平台账期，分销验收保持待完成，不把权限窗口出现视为通过。

平台若要求先发布才能测真实入口，先完成 A/C 并只开放普通售票，再做 B3；B3 未完成前不启动正式达人推广或直播销售。未开启分销不妨碍普通售票。

## C：发布前核对（工程与运营各自负责）

- [ ] 工程：本次提交 CI、部署及 readiness 一致；确认备份和密钥可用、在隔离副本完成恢复验证，有可执行的版本回滚步骤。不得拿线上订单作恢复演练。
- [ ] 工程：按首发预计同时下单/核销量完成容量检查，至少一段 8 小时稳定运行观察，记录查询任务、退款任务、日志和磁盘无持续异常。没有计划客流数据时先限定小范围开放，不直接宣称支持大规模直播峰值。
- [ ] 运营：正式商品审核通过，票名、价格、库存、有效日期、景区/检票点、营业信息、退款规则、客服电话和用户隐私说明已核对。
- [ ] 发布人员：最新原生包完成平台要求的隐私/权限申报和版本审核，确认发布的是已验收的版本。GitHub Actions 不代替此步骤。
- [ ] 发布后冒烟：通过普通用户真实入口再做一笔“购买→出票→未使用退款”或“购买→出票→核销”，确认无体验版/发布版环境差异，随后才扩大开放。

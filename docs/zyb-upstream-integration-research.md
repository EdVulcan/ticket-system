## 2026-09-13 重新开发：当前执行口径

复查修复（本地，未推送）：上游取消成功或管理员特殊退票后，资金退款明确失败也保留原票券占用和二维码隐藏。后台“恢复款项退款”复用微信/支付宝原任务；小红书仅在原售后已确认失败时，由本景区初始管理员创建带原退款引用的新资金申请，在同一事务交接票券占用及供应商退款关联。原失败请求与密文保留，重复/并发恢复返回同一新申请；普通入口仍不能绕过失败售后限制。混合退款不能在上游已退票后关闭并解锁。

出票失败增加“查单并恢复出票”：先查询原单；已存在只恢复查询/取码，只有明确未成单且管理员确认后，才允许 worker 使用原订单号重新发码。网络错误或订单号格式错误不当作未成单。查询期间有租约，退款占用或已出票时拒绝恢复。供应商查询失败不阻断后台读取本地任务。供应草稿优先回读，窗口供应入口及启用能力已关闭，窗口订单始终本地出票；改签继续使用本系统原售后操作，由人工同步另一套系统，不增加自动联动。

复查修复验证：服务层全量、API/路由、智游宝协议测试通过；新增回归覆盖资金失败持续锁票和隐藏二维码、恢复失败回滚、并发恢复只产生一个新申请、原失败售后不可复活、混合退款不可错误解除锁票、未发码订单退款、原单查验后恢复出票、窗口隔离、草稿回读及人工改签不改票码。迁移专项、`go vet`、`go build`、管理端构建通过；6 项 Playwright 测试通过，包含查询供方失败后读取本地恢复入口。首次并行验证中一个原有并发核销用例因写库超时失败，单独重跑及最终顺序服务层全量回归均通过，未放宽业务超时。本轮仍未推送或访问生产。

本节优先于下方历史研究方案。依据用户重新提供的业务对话，智游宝仅替代核销码生成，并提供查单及取消能力；不新增核销前供应商检查，不合并两边次数，不建立另一套外部票权。

- 共用连接维护接口、企业编码、用户名、加密密钥和环境；新建为草稿，商家显式启用。产品仅设置出票开关、连接及上游商品编码。普通商品编辑不覆盖供应设置，关闭连接仅限制新销售，历史订单仍可查单和退款。
- 售出时固化供应身份。支付后的 `pending_provider` 票由独立 worker 处理；普通支付回调保持原样。首次发送前持久保存请求及尝试时间；自动重试只查询原订单，人工恢复需按上段核对。出票成功先保存供应商主/子订单号，再获取直接 Base64 图片并解码，在一个事务中写入现有 Ticket 与对应 TicketEntitlement 的票码字段。
- 新旧设备识别同一码，各自核销。订单管理按分钟主动查询，可手动刷新；核销明细中的最早实际时间与本地首次有效核销取最早值用于展示。不将查询时间、最后一次核销时间伪装成首次使用，不写入虚构本地核销记录或变更结算。
- 退款预检只读，不取消供应商订单。现有退款事务先校验金额、政策和权限并占用票券，之后退款 worker 先整单取消智游宝、确认退票结果，再执行原资金退款及既有业务结转。取消请求结果不明保留原申请和票券占用；不会再次发送取消。现金、数字及混合退款使用相同上游前置处理，纯本地退款维持原行为。
- 供应商已使用、不可退或无法确认时，游客不能自动退款；履约景区初始管理员可显式确认并填写原因。原退款处理中发现冲突可从线上订单详情确认继续同一退款任务。特殊退款记录 `override`，不冒充供应商已取消；本地误核销退款沿用原权限。
- schema 118 在原供应快照中增加执行进度和供应商身份字段，不增加独立任务表，不删除历史占位表。旧订单保持本地模式，票码、金额、库存、支付、核销及退款事实不重建。部署继续使用现有升级前备份、事务迁移和 SHA/schema 就绪核验。

当前适配边界：普通线上门票，一个订单一个上游票种；一人一码为单张，整单一码复用现有数量和检票规则。线上上游订单联系人必须真实完整；窗口不采集联系人、不对接供应商。改签由人工分别操作两边，沿用本系统现有日期/库存处理并保留原票码；上游订单不能直接作废，须退票。二维码超过现有 50 字符字段或图片解码失败时明确待处理，不截断或生成替代码。

本地模拟接口验证不代表供应商正式验收。正式启用需验证真实出票/取图、两个区域独立扫码、普通退票取消结果、异常恢复及管理员特殊退款。当前没有提交真实供应商订单，也没有修改生产数据库。

## 1. 过渡目标

合作景区旧区域继续使用智游宝的既有设备，新区域使用本系统的设备和检票点。对于明确配置为外部供票的产品，游客取得一份由智游宝签发的固定核销码；旧区域和新区域均可读取同一核销码，但各自只执行自身已配置的检票点与票权益规则。

这不是把智游宝的检票点、票规或订单状态复制进本系统，也不是把本系统作为智游宝的下游渠道。现有多租户、供应履约、票权益、退款和结算规则继续以开发基线为准。

- 当前项目没有智游宝上游供应适配器、外部采购订单、外部票码或外部供应对账的已启用实现。本轮未改动业务代码，也不应据此宣称可对接生产。

## 3. 已确认的业务规则

### 3.1 产品和出票方式

1. 产品**默认**由本系统生成核销码。
2. 只有产品明确开启上游供应、选择具体供应连接，并配置对应的上游商品后，才向该上游系统出票并复用其实际核销码。
3. 已开启但配置不完整、上游出票失败或尚未取得完整核销码时，订单进入明确的待处理/失败路径；不得静默回退为本地出码。
4. 订单必须固化销售时的供应方式、供应连接、上游商品、双方订单身份、数量、游玩日期、外部票码和请求/响应快照。以后关闭、替换供应商或修改商品映射，只影响新订单，不改写已售票。

### 3.2 同码核销和展示

- 同一外部核销码可被本系统关联为本地票权益的核销入口。智游宝旧区域与本系统新区域分别维护自己的检票点、次数和剩余权益；任一侧的使用不能凭空扣减另一侧权益。
- 多张票可能统一关联同一个上游码，不强行虚构逐票外部映射；但本地订单数量和本地核销次数仍必须按已售快照准确处理。
- 任一区域已经使用后，订单对外可显示“已使用”，但二维码应继续显示，使其他区域在其剩余权益内仍可核销。两边都使用过后是否还能通行，仍由各自剩余次数决定。
- 本系统发生退款占用时暂停展示并阻止本地核销；退款成功后关闭展示并使本地票权失效。对于外部供票，还必须完成或确认上游失效，不能把隐藏页面二维码当作已撤销外部票权。

### 3.3 退款和重试

- 对外仍按整单处理：任一区域已使用即阻止普通整单退款；未使用的退票申请由系统自动审核通过，已使用自动拒绝。
- 上游退票首次响应不是最终完成事实。必须等待上游查询/确认结果后，才完成本地原路退款和票权、库存、资金事实的既有处理。
- 下单请求一旦发送，即保存不变的请求内容。响应超时后只查询原单；重复订单号被拒绝不代表原单失败，不能换一个订单号再次出票。

## 4. 实现方向

后续应以独立的上游供应适配器和采购履约模型承接 XML 协议，转换到现有统一订单、票权益、退款、库存和事件模型。外部字段不得反向成为核心订单的唯一事实，也不得复用下游渠道适配器来实现上游采购。

回调只作为触发查询与唤醒恢复任务的信号。验签、去重、原始报文审计和主动查询确认应分别处理；不应直接按回调中的数量创建本地核销或退款事实。查询必须遵守上游限流，重试和恢复任务应可跨进程重启继续。

### 4.1 本地基础预置（2026-09-10，待发布）

- 线上/窗口门票的“供应”入口可创建智游宝供应连接、保存上游商品映射草稿。草稿不改变本地出票；API 与数据库均拒绝正式启用，避免未经联调的配置影响现有销售。连接与下游渠道账号分开。
- `ProductSupplyConfig.ActiveMappingID` 为空表示本地出票；以后启用通过原子切换已验收映射完成。配置不放进普通商品编辑请求，避免旧客户端编辑票种时清掉供应设置。
- schema 117 创建逐订单明细的不可变供应快照。已有明细全部按本地供应补齐，不从当前商品反推；新明细在同一事务自动保存供应、销售租户、景区、商品版本及环境。供应快照每个明细一份，仅固化原始供应身份，不增加换票版本链；改签保留票种和供应身份，日期/场次变化沿用现有售后记录，部分改签按拆分明细保存同源快照。原订单、票码、价格、库存、支付、退款事实不重建。酒店明细沿用其现有零景区/票版本字段，不据此生成门票。
- 外部凭证与本地票码独立，预留加密完整载荷、查找摘要和一对多绑定结构。本批没有取码、写入凭证或核销路由，数据库拒绝实际写入外部凭证；不能把表存在视为已支持智游宝核销。待人数口径和协议确认后再打开带完整归属校验的写入路径。
- 小程序 `completed` 不再单独隐藏服务端返回的已签发二维码；退款占用和签发闸门仍保留，实际通行仍由检票点规则决定。
- 部署前向升级先生成可校验的数据库备份，再事务执行 DDL、旧单回填和版本标记。重复执行不补第二份快照；孤儿订单明细导致迁移中止并回滚。Actions 最后核对运行代码 SHA 与当前数据库版本，不以静态页面可打开判断升级成功。

### 4.2 售后范围收口与审计修复（2026-09-10，未推送）

# 智游宝上游供票过渡研究记录

> 状态：2026-09-10 完成首轮研究，**尚未开发或启用**。智游宝在本方案中是外部上游供票系统，不是下游销售渠道；本记录只为后续独立供应适配器和现场联调提供事实、已确认规则与待补资料的边界。

## 1. 过渡目标

合作景区旧区域继续使用智游宝的既有设备，新区域使用本系统的设备和检票点。对于明确配置为外部供票的产品，游客取得一份由智游宝签发的固定核销码；旧区域和新区域均可读取同一核销码，但各自只执行自身已配置的检票点与票权益规则。

这不是把智游宝的检票点、票规或订单状态复制进本系统，也不是把本系统作为智游宝的下游渠道。现有多租户、供应履约、票权益、退款和结算规则继续以开发基线为准。

## 2. 已确认的证据

### 2.1 文档和样本

- 已阅读 `E:\code\zyb\2020.4.30智游宝门票接口文档 分时.docx`。它覆盖发码、订单/检票查询、票码图片或链接、核销通知、退票申请及退票结果查询；它不是该景区当前合同或智游宝全量产品说明。
- 分销出票响应中同时出现外部主订单、子订单、商品编码、数量、游玩日期和辅助核销编号。不同接口使用的订单身份不同：部分查询/取码请求使用我方提交的第三方订单号，核销明细查询使用第三方子订单号。因此后续必须保存双方订单身份和请求快照，不能只保留一个“外部订单号”。
- 实际票码图片已解码得到一段固定的二维码载荷（已脱敏）。该值是扫码器实际读取并由系统执行核销的内容；它不是出票响应里的辅助编号本身。现阶段只按图片/链接取得并解码的完整内容保存，**不推测或硬编码票码拼接规则**。
- 2020 文档中的订单完结、核销、退票三类回调签名拼接方式存在差异。后续适配器必须按通知类型分别验签，不能以一种签名规则覆盖全部回调。
- 文档已提示下单超时后的恢复原则：复用原第三方订单身份查询原单，而非创建新订单。用户已确认：相同订单号重复提交会被拒绝。

### 2.2 当前代码边界

- 当前项目没有智游宝上游供应适配器、外部采购订单、外部票码或外部供应对账的已启用实现。本轮未改动业务代码，也不应据此宣称可对接生产。
- 当前“订单完成即隐藏二维码”的表现被识别为不符合多检票点票权益的需求，尚未修复。二维码展示应由可用权益和退款占用/成功事实决定，不能只由订单完成投影决定。

## 3. 已确认的业务规则

### 3.1 产品和出票方式

1. 产品**默认**由本系统生成核销码。
2. 只有产品明确开启上游供应、选择具体供应连接，并配置对应的上游商品后，才向该上游系统出票并复用其实际核销码。
3. 已开启但配置不完整、上游出票失败或尚未取得完整核销码时，订单进入明确的待处理/失败路径；不得静默回退为本地出码。
4. 订单必须固化销售时的供应方式、供应连接、上游商品、双方订单身份、数量、游玩日期、外部票码和请求/响应快照。以后关闭、替换供应商或修改商品映射，只影响新订单，不改写已售票。

### 3.2 同码核销和展示

- 同一外部核销码可被本系统关联为本地票权益的核销入口。智游宝旧区域与本系统新区域分别维护自己的检票点、次数和剩余权益；任一侧的使用不能凭空扣减另一侧权益。
- 多张票可能统一关联同一个上游码，不强行虚构逐票外部映射；但本地订单数量和本地核销次数仍必须按已售快照准确处理。
- 任一区域已经使用后，订单对外可显示“已使用”，但二维码应继续显示，使其他区域在其剩余权益内仍可核销。两边都使用过后是否还能通行，仍由各自剩余次数决定。
- 本系统发生退款占用时暂停展示并阻止本地核销；退款成功后关闭展示并使本地票权失效。对于外部供票，还必须完成或确认上游失效，不能把隐藏页面二维码当作已撤销外部票权。

### 3.3 退款和重试

- 对外仍按整单处理：任一区域已使用即阻止普通整单退款；未使用的退票申请由系统自动审核通过，已使用自动拒绝。
- 上游退票首次响应不是最终完成事实。必须等待上游查询/确认结果后，才完成本地原路退款和票权、库存、资金事实的既有处理。
- 下单请求一旦发送，即保存不变的请求内容。响应超时后只查询原单；重复订单号被拒绝不代表原单失败，不能换一个订单号再次出票。

## 4. 实现方向（尚未开工）

后续应以独立的上游供应适配器和采购履约模型承接 XML 协议，转换到现有统一订单、票权益、退款、库存和事件模型。外部字段不得反向成为核心订单的唯一事实，也不得复用下游渠道适配器来实现上游采购。

回调只作为触发查询与唤醒恢复任务的信号。验签、去重、原始报文审计和主动查询确认应分别处理；不应直接按回调中的数量创建本地核销或退款事实。查询必须遵守上游限流，重试和恢复任务应可跨进程重启继续。

## 5. 待智游宝 BD 补充确认

用户已向智游宝 BD 索取新文档。在获得协议、合同约束和测试环境前，实施保持暂停。需要重点确认：

- 当前景区实际开通的下单、取码、订单查询、核销明细、核销回调、退票及退票结果查询接口、字段与验签版本。
- 三类回调的重试、去重键、签名字段和失败处理；回调中的核销数量是本次量还是累计量，以及多区域/套票时的具体口径。
- 查询限流、订单状态枚举及退票查询的完整失败码，尤其是“审核未通过”等最终失败状态。
- 退票申请与旧区域扫码并发时，上游何时锁票、何时禁止检票，以及最终状态的优先级。
- 统一码对应多份票时，旧区域每次扫码如何扣人数、能否分批使用，以及本地新区域需如何匹配相同的消费口径。
- 能否约定退款由本系统统一发起，以及智游宝后台能否绕过本地已使用检查；如果保留旧后台退款入口，需要进一步确定外部退款通知、失效同步和异常处置方案，不能只依赖本地审核。

# 微信商业 Storefront 集成状态

> 状态：公开微信商业 storefront 已完成会话、目录、购物车、订单、服务端地址快照、退款申请和支付边界实现，并通过跨租户及支付状态机回归。支付下单、支付/退款通知验签解密、主动查单、持久化尝试与重启恢复已在本地代码闭环；真实微信登录、商户证书、支付/退款通知和履约联调仍是独立准入项，不能宣称已接入生产。

## 权威系统

CloudBase 不再作为商业商品、SKU、库存、购物车、订单、支付或退款的运行时数据源。商业交易的唯一权威是本 SaaS 平台及其 PostgreSQL 数据库；微信入口只负责展示和提交受限请求，不能在客户端或 CloudBase 侧维护第二份可写业务事实。

商业订单继续使用独立的 `commerce_*` 模型和 service。它们不复用景区票务 `Order`、票权、票码、景区库存、核销或票务结算事实。餐饮和通用电商也不能混合为一个订单。

## 租户和渠道绑定

公开入口必须从服务端解析租户和渠道账号。客户端传入的 `tenant_id`、`channel_account_id`、业务类型、履约地点、客户身份、金额、折扣、支付状态和退款状态都不是权威字段。

微信小程序账号沿用平台的渠道中心，不新增独立的小程序账号体系。已启用餐饮或通用电商能力的租户可以在渠道中心创建或更新 `wechat_miniapp` 账号；携程、小红书等景区票务渠道仍按原有供应商/分销商能力授权。服务端按账号类型拒绝商业租户创建或修改票务渠道，也拒绝对微信商业账号添加景区票务商品映射。账号的 AppSecret 只在渠道服务中加密保存，商业工作台只读取脱敏账号并负责 storefront 业务绑定。

每个发布配置绑定一个租户、一个渠道账号、一个商业业务类型和一个履约地点。当前实现对一个微信渠道账号只允许一个 storefront 业务配置；若同一租户同时经营餐饮和电商，应分别配置渠道账号/发布配置，避免游客会话在两个履约域之间串用。渠道账号停用、发布绑定停用、租户不可用或对应商业 capability 暂停时，目录、购物车、checkout、订单查询和售后入口都必须 fail closed；历史订单保留，但不能借已有凭据继续创建新交易。

租户后台的商业工作台“**小程序发布**”页通过受保护的 `/api/v1/commerce/storefront-bindings` 读取和保存发布绑定，并通过 `/api/v1/commerce/storefront-channels` 读取本租户可选的微信小程序账号。保存时只选择本租户已有的 `wechat_miniapp` 渠道账号、已启用的商业能力和同业务类型的履约地点；AppID/AppSecret 仍由渠道账号配置接口维护，绑定接口不会接收或返回密钥。保存会写租户审计，停用绑定只阻止新游客会话和交易，不删除历史订单。账号创建和密钥维护仍在渠道账号边界完成。

游客会话必须同时绑定租户和渠道账号。session token 只保存不可逆 hash，必须有过期和撤销状态；请求中的 customer、cart、order、售后申请只能在当前 session 的 tenant/account 范围内解析。过期、撤销、账号不匹配或租户/capability 不可用时，不得通过改写请求体字段恢复访问。

## 游客地址与订单快照

公开地址已接入 SaaS PostgreSQL：地址按租户、渠道账号会话生成的游客主体哈希隔离，支持校园地址和普通快递地址的新增、编辑、删除及默认地址切换。checkout 只接收服务端地址编号，服务端再次校验当前会话归属和业务类型，并把地址字段写入订单快照；客户端提交的自由文本地址不作为订单事实。地址修改或删除不会改变已有订单快照。

## 金额、库存和幂等

商品、SKU、选项、库存、履约地点和价格由 SaaS 服务端读取。checkout 只接收联系人、地址、履约方式和幂等键等必要输入，并从已绑定购物车重新计算金额；客户端伪造金额、折扣、商品所属租户、业务类型、地点或库存数量必须被忽略或拒绝。

同一租户、渠道账号、客户和购物车的 checkout 请求必须以持久化幂等键收敛到同一个商业订单。重试不能重复预占库存或产生第二个商业订单；跨租户、跨账号或不同请求内容复用幂等键必须拒绝。

配送订单的幂等重试只比较下单时保存的地址快照编号和联系人事实，不重新读取或信任客户端地址文本；地址被修改或删除后，原幂等键仍返回原订单，换用不同地址编号则拒绝。

## 支付与退款准入

当前本地商业订单状态机提供支付/退款边界、人工复核和重启恢复所需的持久化事实。微信支付下单、签名验签、通知解密、主动查单、退款申请、退款回调和金额校验已完成代码实现；真实商户凭据、真机支付、通知重放及生产金额验收仍未完成。

在可信 provider confirmation 到达前，退款只能停留在 `requested`、`approved` 或 `processing` 等处理中状态；普通租户请求不能直接把退款改成 `completed`、把订单标记为 `refunded` 或恢复库存。provider reference 和 provider amount 必须由认证的支付适配器写入并与原订单快照匹配，重复 confirmation 必须幂等。

真实支付凭据、微信商户配置、回调重放防护、进程重启恢复、通知和生产履约 worker 通过现场/沙箱验收后，才能开放公开 storefront。此前应保持入口关闭或明确返回未接入状态，并持续运行跨 tenant/account、session、capability、金额、checkout 幂等、票务域隔离和退款状态回归测试。

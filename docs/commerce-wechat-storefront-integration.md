# 微信商业 Storefront 集成状态

> **商家联系人（schema 141，本地实现）**：微信小程序的“联系商家”属于 `wechat_miniapp` 渠道账号，不属于餐饮或电商商品，也不要求为两个业务各维护一份。租户可为渠道账号配置个人微信或企业微信、展示名称、微信号和系统托管的 JPG/PNG 二维码，并单独启用或停用。启用必须有二维码；停用时公共接口不返回联系人、微信号或图片地址。管理端的联系人图片按租户/渠道账号隔离，上传内容经过格式、大小和图片解码校验，公共读取路径只允许系统生成的文件名。公共图片路由每次读取当前租户、渠道账号状态和精确的托管 URL；停用、换码、租户/账号失效或文件缺失均返回 404，联系人图片不使用长期 immutable 缓存。

小程序在“我的”页只显示一个“联系商家”入口。入口由服务端 `GET /api/v1/storefront/wechat/contact` 的 `available` 决定；底部弹层提供二维码长按识别、查看大图和复制微信号，不把加微信动作当作会员绑定，也不暴露后台配置入口。餐饮和电商共用同一个微信渠道账号时共享这套联系人配置。

> 状态：公开微信商业 storefront 已完成账号级会话、餐饮/电商目录、购物车、服务端配送报价、订单、地址快照、用户取消/退款/确认收货、优惠券、分享助力和物流时间线，并通过跨租户及支付状态机回归。支付下单、支付/退款通知验签解密、主动查单、持久化尝试与重启恢复已在本地代码闭环；真实微信登录、商户证书、支付/退款通知、商家提示音和履约联调仍是独立准入项，不能宣称已接入生产。

## 权威系统

CloudBase 不再作为商业商品、SKU、库存、购物车、订单、支付或退款的运行时数据源。商业交易的唯一权威是本 SaaS 平台及其 PostgreSQL 数据库；微信入口只负责展示和提交受限请求，不能在客户端或 CloudBase 侧维护第二份可写业务事实。

商业订单继续使用独立的 `commerce_*` 模型和 service。它们不复用景区票务 `Order`、票权、票码、景区库存、核销或票务结算事实。餐饮和通用电商也不能混合为一个订单。

## 租户和渠道绑定

公开入口必须从服务端解析租户和渠道账号。客户端传入的 `tenant_id`、`channel_account_id`、业务类型、履约地点、客户身份、金额、折扣、支付状态和退款状态都不是权威字段。

微信小程序账号沿用平台的渠道中心，不新增独立的小程序账号体系。已启用餐饮或通用电商能力的租户可以在渠道中心创建或更新 `wechat_miniapp` 账号；携程、小红书等景区票务渠道仍按原有供应商/分销商能力授权。服务端按账号类型拒绝商业租户创建或修改票务渠道，也拒绝对微信商业账号添加景区票务商品映射。账号的 AppSecret 只在渠道服务中加密保存，商业工作台只读取脱敏账号并负责 storefront 业务绑定。

### 真实手机号授权（本地已接入，待真机验收）

游客登录后由小程序原生 `button open-type="getPhoneNumber"` 主动触发授权。小程序只把平台返回的一次性 `code` 发送到 `POST /api/v1/storefront/wechat/member/verify-phone`，不提交手机号。服务端使用渠道账号的加密 AppSecret 获取 `access_token`，调用微信 `getuserphonenumber`，并校验返回的 `watermark.appid` 与当前账号一致；登录会话同时保存加密 `openid`，若兼容平台响应额外返回 `openid` 则比较一致性，但不把官方响应中可能缺失的可选字段当成失败条件。成功后服务端在同一事务内写入可信手机号、会员授权和非敏感幂等事件；营销授权永远不会由此推断。旧会话没有加密 `openid` 绑定时返回登录失效，重新登录即可升级。

每个发布配置绑定一个租户、一个渠道账号、一个商业业务类型和一个履约地点。同一微信渠道账号可分别发布餐饮和电商；游客以 AppID 和微信身份登录一次，服务端返回已授权业务列表。目录、购物车、配送报价和 checkout 在请求级显式选择业务域，服务端重新验证当前绑定、租户能力和履约地点；客户端选择值只负责路由，不能成为授权。停用或改绑只阻断对应业务的新交易，历史订单、支付查询、退款和物流仍按订单不可变快照访问。

租户后台的商业工作台“**小程序发布**”页通过受保护的 `/api/v1/commerce/storefront-bindings` 读取和保存发布绑定，并通过 `/api/v1/commerce/storefront-channels` 读取本租户可选的微信小程序账号。保存时只选择本租户已有的 `wechat_miniapp` 渠道账号、已启用的商业能力和同业务类型的履约地点；AppID/AppSecret 仍由渠道账号配置接口维护，绑定接口不会接收或返回密钥。保存会写租户审计，停用绑定只阻止新游客会话和交易，不删除历史订单。账号创建和密钥维护仍在渠道账号边界完成。

游客会话必须同时绑定租户和渠道账号，但不绑定可变发布配置。session token 只保存不可逆 hash，必须有过期和撤销状态；请求中的 customer、cart、order、售后申请只能在当前 session 的 tenant/account 范围内解析。过期、撤销、账号不匹配时不得通过改写请求体字段恢复访问；能力或绑定暂停时拒绝新交易，但本人历史订单仍可查询和售后。

## 游客地址与订单快照

公开地址已接入 SaaS PostgreSQL：地址按租户、渠道账号会话生成的游客主体哈希隔离，支持本地配送地址和普通快递地址的新增、编辑、删除及默认地址切换；历史 `CAMPUS` 地址继续兼容，但新客户端统一使用 `DELIVERY`。checkout 只接收服务端地址编号，服务端再次校验当前会话归属和业务类型，并把地址字段写入订单快照；客户端提交的自由文本地址不作为订单事实。地址修改或删除不会改变已有订单快照。

## 金额、库存和幂等

商品、SKU、选项、库存、履约地点和价格由 SaaS 服务端读取。checkout 只接收联系人、地址、履约方式和幂等键等必要输入，并从已绑定购物车重新计算金额；客户端伪造金额、折扣、商品所属租户、业务类型、地点或库存数量必须被忽略或拒绝。

同一租户、渠道账号、客户和购物车的 checkout 请求必须以持久化幂等键收敛到同一个商业订单。重试不能重复预占库存或产生第二个商业订单；跨租户、跨账号或不同请求内容复用幂等键必须拒绝。

配送订单的幂等重试只比较下单时保存的地址快照编号和联系人事实，不重新读取或信任客户端地址文本；地址被修改或删除后，原幂等键仍返回原订单，换用不同地址编号则拒绝。

餐饮配送/自取和电商快递均必须先调用服务端报价。报价固定租户、渠道账号、业务域、客户、履约地点、购物车商品小计、地址、配送区域、时段及费用，并以短时单次令牌交给 checkout 消费。餐饮支持按行政区配置区域运费、起送金额、时段、截止时间和容量；电商支持默认运费与包邮门槛。修改购物车或跨客户、跨业务、跨地点复用报价均拒绝。

餐饮配送时段按服务日期统一计数：有效未过期报价和已提交订单都占用容量，未支付取消/超时及未履约全额退款释放占用；同一天不同时间表示不能绕过容量。配送区域和时段仅属于餐饮，本地电商只读取快递费与包邮配置，不能创建餐饮配送配置。

分享助力响应包含服务端确认的发起人和助力人奖励摘要。分享令牌以哈希查找、加密保存以支持幂等重试；小程序只展示返回的奖励金额、门槛和有效期，不使用本地默认值或估算值。优惠选择必须提交具体权益编号，最终折扣仍由 checkout 事务重新校验并写入订单调整快照。

当前不开放零元支付单。优惠抵扣后应付为零时，checkout 会整体回滚并返回不可结算，不会创建无法进入微信支付又长期停留在未支付状态的订单。

## 支付与退款准入

当前本地商业订单状态机提供支付/退款边界、人工复核和重启恢复所需的持久化事实。微信支付下单、签名验签、通知解密、主动查单、退款申请、退款回调和金额校验已完成代码实现；真实商户凭据、真机支付、通知重放及生产金额验收仍未完成。

在可信 provider confirmation 到达前，退款只能停留在 `requested`、`approved` 或 `processing` 等处理中状态；普通租户请求不能直接把退款改成 `completed`、把订单标记为 `refunded` 或恢复库存。provider reference 和 provider amount 必须由认证的支付适配器写入并与原订单快照匹配，重复 confirmation 必须幂等。

退款回调公网地址在创建支付机构退款尝试之前验证；配置缺失时请求保留为可恢复的 `requested`，不会生成一个实际未提交却显示处理中的尝试。退款锁建立后，服务端同时禁止发货、追加物流推进和确认收货；若履约先开始，则退款请求不能落库。支付机构明确失败时订单恢复为可再次处理的拒绝状态，结果未知时继续由持久任务主动查询，不能提前释放库存或允许履约绕过退款锁。尝试已落库但调用微信前进程中断时，worker 使用同一个 `out_refund_no` 和原始不可变参数重提，不生成第二笔退款身份。

游客端只展示服务端返回的 `available_actions`：未支付订单可取消，未开始履约的已支付订单可申请退款，配送到达或快递送达后可确认收货。电商发货通过独立包裹和追加式物流节点推进，商家不能绕过物流时间线直接把订单标为完成。

商家新订单提醒来自支付成功事务写入的 durable outbox；后台通知中心按可见状态增量补拉并允许操作员主动开启提示音。通知已读不等于接单，订单工作台仍以真实订单履约状态为准。

真实支付凭据、微信商户配置、回调重放防护、进程重启恢复、通知和生产履约 worker 通过现场/沙箱验收后，才能开放公开 storefront。此前应保持入口关闭或明确返回未接入状态，并持续运行跨 tenant/account、session、capability、金额、checkout 幂等、票务域隔离和退款状态回归测试。

# 租户统一客户与会员中心设计

> 状态：第一阶段模型、迁移、领域身份解析、后台查询、自营入口订单归属和微信/小红书真实手机号授权适配已实现；真实平台验收和后续会员权益仍未完成。本文继续作为实现边界和验收依据。
>
> 确认日期：2026-09-21。
>
> 适用范围：租户自营、直接接入的微信小程序、小红书自研小程序、App 和官网等客户入口。OTA、旅行社、分销商、外部平台导入订单、匿名窗口订单不纳入租户会员关系。

本文是平台身份域的细化设计，服从 [多租户开发基线](./platform-multitenancy-development-guide.md)。票务、酒店、餐饮和电商继续保留各自的订单、履约、退款、库存和结算状态机；会员中心只负责租户客户身份、会员资格和跨自营入口的身份关联，不能成为绕过原业务授权的捷径。

## 1. 目标和已确认结论

每个租户拥有一套独立的客户与会员中心。同一租户自营的多个小程序、App 或官网可以把各自的登录身份关联到同一个租户客户；餐饮、电商、景区自营销售和自营酒景产品可以共享该客户身份。

以下结论已经固定，后续实现不得自行改变：

1. 租户是客户与会员数据的唯一归属边界；跨租户不共享、不检索、不合并会员。
2. 所有租户自营、直接接入并完成服务端认证的终端用户进入统一客户管理模块。
3. 首次从合格自营入口登录时创建 `membership_status=provisional` 客户记录；只有完成可信手机号验证和会员授权后才成为 `membership_status=active` 的正式会员。
4. 微信 `openid`、小红书用户标识、App 用户 ID、现有 `CustomerID` 都只是渠道身份，不能作为租户会员主键。
5. 手机号是可验证联系方式，不是会员主键。姓名、订单联系人、游客、入住人、收货人和普通手机号输入都不能触发建档或合并。
6. 由 OTA、旅行社、分销商、外部销售平台或人工导入作为获客/销售来源创建的订单不创建会员、不关联会员，也不提供订单认领入口。租户自营入口销售、但由智游宝等外部供应商履约的订单仍属于租户自有客源，可以关联会员。
7. 是否属于自营客户不能根据订单 `channel` 字符串、联系人手机号或客户端字段推断，必须由服务端认证入口和平台控制的渠道配置共同决定。
8. 现有渠道客户、会话、购物车、地址、促销和订单身份继续保留；统一会员层是向上增加的关联层，不替换现有字段。
9. 订单只增加可空的会员归属；会员绑定不能改写订单联系人、游客、商品、价格、支付、票权、履约、退款或结算快照。
10. 会员中心第一阶段不做积分、等级、储值、成长值和营销自动化；店铺级跨业务优惠券与助力活动属于商业营销中心，不改变会员身份归属和渠道边界。

## 2. 当前代码基础和差距

当前代码已经完成第一阶段的会员域落地，并继续保留原有渠道身份基础：

- `CommerceCustomerSession` 按租户、渠道账号和微信 subject 隔离；同一微信小程序内的餐饮和电商共用账号级会话。
- 商业域 `CustomerID` 由渠道账号和 subject 哈希生成，购物车、地址、促销和订单都依赖它。
- `MiniappCustomer` 按租户、渠道账号和小红书用户标识隔离，`XiaohongshuOrderLink` 负责订单归属。
- 景区票务 `Order` 和商业 `CommerceOrder` 已增加可空的同租户会员引用；历史订单不回填。
- `TenantMember`、渠道身份、可信联系方式、授权事件和生命周期事件已迁移到 PostgreSQL schema 143；商业微信会话新增加密 `openid` 绑定，旧会话需重新登录后才能做手机号授权。
- `MemberService` 已接入微信商业 storefront 和小红书自营小程序登录/下单；后台已提供租户隔离的列表、详情、掩码手机号和冻结/解冻。
- 微信使用 `getuserphonenumber` 服务端接口，小红书使用登录会话 `session_key` 解密 `getPhoneNumber` 回调；两条链路都只接受当前会话的服务端身份，不接受客户端手机号或 session key。App/官网适配、导出和安全复核入口仍未完成，不能把当前阶段误认为完整会员权益系统。

因此后续开发仍不应重写登录和订单，只能在现有身份之上补齐受信手机号授权、其他自营入口适配和运营验收；合格自营订单继续保存可空归属。

## 3. 统一术语

### 3.1 渠道身份

渠道身份表示“某个受信渠道账号认证了某个用户”。例如一个微信小程序 `openid`、一个小红书自研小程序用户或一个 App 账号。

渠道身份继续负责当前会话、本人订单访问、购物车、地址等入口级授权。不同渠道身份默认互不相同，不能因为姓名或手机号文本相同就视为同一人。

### 3.2 租户客户

租户客户是该租户范围内稳定的客户主档案。首次从合格自营入口完成登录后建立 `provisional` 客户，并绑定一个渠道身份。

`membership_status=provisional` 只表示该用户已经从租户自营入口出现，不表示已经完成会员授权，也不允许营销触达。后台显示名称应为“渠道客户”或“待认证客户”，不能误标为正式会员。

### 3.3 正式会员

租户客户完成可信手机号验证、同意当前会员协议后转为 `membership_status=active`。会员授权和营销授权必须分开记录；加入会员不等于同意营销短信、电话或广告推送。

### 3.4 履约人员快照

订单联系人、游客、入住人、收货人、团队成员和司机等继续是订单或履约快照。它们不是租户客户身份，也不随会员资料修改而变化。

### 3.5 外部渠道客户

OTA、旅行社、分销商或其他平台带来的用户属于外部渠道客源。系统只保存履约必需的订单快照，不将其转为租户客户或会员。

## 4. 归属判断和渠道准入

### 4.1 双重准入

只有同时满足以下条件的入口才能创建或解析租户客户：

1. 请求来自服务端已实现并认可的自营身份适配器；
2. 对应 `ChannelAccount` 或未来的客户端注册被平台标记为允许会员身份。

建议在渠道账号增加平台控制的 `member_mode`：

- `disabled`：不参与统一客户中心，默认值；
- `first_party`：租户自营入口，可建立渠道身份和租户客户关联。

租户管理员可以查看该状态，但不能仅靠普通前端请求把外部渠道改成 `first_party`。平台必须根据账号所有权、认证方式和用户授权能力决定是否开放。

### 4.2 准入矩阵

| 入口 | 是否建立客户身份 | 新订单是否关联会员 | 说明 |
|---|---:|---:|---|
| 租户自营微信小程序 | 是 | 是 | 必须从服务端微信登录会话解析 |
| 租户自营 App / 官网 | 是 | 是 | 必须有独立受信认证适配器 |
| 租户自研小红书小程序页面 | 是 | 是 | 必须存在当前 `MiniappCustomer` 登录身份 |
| 小红书纯平台回调、导入或无法证明当前自研小程序用户的订单 | 否 | 否 | 担保支付本身既不证明也不否定自营关系，关键是是否有受信用户会话 |
| 携程及其他 OTA API 订单 | 否 | 否 | 只保留联系人和游客快照 |
| 分销商销售订单 | 否 | 否 | 客户关系归销售方，不归履约供应商 |
| 旅行社团队订单 | 否 | 否 | 团队成员不是会员 |
| 外部供应商作为销售来源推送或导入的订单 | 否 | 否 | 外部销售来源不转为租户会员 |
| 租户自营入口销售、外部供应商履约的订单 | 是 | 是 | 获客入口决定会员归属，履约供应关系不决定 |
| 窗口/POS 匿名订单 | 否 | 否 | 当前窗口售票保持匿名 |
| 人工导入订单 | 否 | 否 | 禁止依据手机号自动关联 |

小红书的判断以实际入口为准：用户通过租户自研小程序登录并在该会话中下单，可以关联会员；只有平台回调或外部订单数据、没有当前受信客户会话时，不得关联。

小红书会员准入事实必须在原始订单创建时，由当前受信 `MiniappCustomer` 会话判定并固化。担保支付、审核、退款等后续平台回调、订单导入和恢复任务不得新建或提升会员归属；仅存在 `MiniappCustomerID`、`XiaohongshuOrderLink`、平台订单号或联系人资料，不足以证明订单来自合格自营会话。

## 5. 数据模型

以下名称是当前实现和后续扩展的稳定契约。实现时如当前 schema 已前进，应使用下一个可用版本，不得硬抢固定版本号。

### 5.1 `tenant_members`

租户客户和会员的稳定主档案：

| 字段 | 含义 |
|---|---|
| `id` | 内部稳定主键，不对游客展示 |
| `tenant_id` | 所属租户，由服务端上下文确定 |
| `member_no` | 租户内唯一、不可猜测的展示编号 |
| `status` | 账户生命周期：`active`、`frozen`、`merged`、`anonymized` |
| `membership_status` | 会员资格：`provisional`、`active`、`withdrawn` |
| `display_name` | 可空展示名，不作为身份依据 |
| `avatar_url` | 可空资料，受授权和隐私策略约束 |
| `registration_channel_account_id` | 首次来源，仅作来源记录 |
| `merged_into_member_id` | 被合并时指向同租户规范会员 |
| `first_seen_at` / `last_seen_at` | 自营入口活动时间 |

约束：

- 唯一 `(tenant_id, member_no)`；
- 建立 `(tenant_id, id)` 唯一索引供复合外键使用；
- `merged_into_member_id` 必须指向同租户且不能指向自身；
- 只有账户 `status=merged` 允许存在合并目标；
- 冻结和解冻只改变账户 `status`，不能丢失原来的 `membership_status`；
- 合并解析必须锁定记录、压平到规范根节点并拒绝环路。

### 5.2 `tenant_member_identities`

租户客户与自营渠道身份的映射：

| 字段 | 含义 |
|---|---|
| `tenant_id` / `member_id` | 同租户会员归属 |
| `provider` | 服务端枚举，例如 `wechat_miniapp`、`xiaohongshu_miniapp`、`app`、`web` |
| `channel_account_id` | 已验证属于该租户的渠道账号或客户端注册 |
| `subject_blind_index` | 渠道用户标识的带密钥盲索引 |
| `blind_index_version` | 盲索引密钥版本 |
| `status` | `active` 或 `revoked` |
| `link_method` | `first_login`、`verified_contact` 或受控恢复方式 |
| `linked_at` / `last_seen_at` / `revoked_at` | 生命周期时间 |

唯一 `(tenant_id, channel_account_id, provider, subject_blind_index)`。同一渠道身份只能指向一个客户；重新启用应更新原记录，不能插入竞争映射。

新表不重复保存原始 `openid` 等敏感值。现有渠道模型需要原文执行平台请求时继续使用其加密字段；统一会员层只保存带密钥盲索引和引用。

渠道身份盲索引使用带密钥 HMAC，输入必须包含租户、渠道账号、provider 和规范 subject。密钥轮换期间必须同时识别当前与上一受支持版本，并在完成唯一性校验后受控重建；不能因为新旧摘要不同产生重复身份映射。

### 5.3 `tenant_member_verified_contacts`

第一阶段只支持已验证手机号：

| 字段 | 含义 |
|---|---|
| `tenant_id` / `member_id` | 同租户会员归属 |
| `contact_type` | 第一阶段固定 `phone` |
| `value_ciphertext` | 加密后的规范手机号 |
| `value_blind_index` | 带密钥盲索引，用于等值查找 |
| `blind_index_version` | 盲索引密钥版本 |
| `encryption_key_version` | 加密密钥版本 |
| `verification_method` | 微信可信手机号、服务端短信验证码等 |
| `verified_at` | 服务端确认时间 |
| `status` | `active` 或 `revoked` |

同一租户内，一个规范手机号同一时间只能属于一个有效会员。PostgreSQL 必须建立 `(tenant_id, contact_type, value_blind_index) WHERE status = 'active'` 部分唯一索引，服务层预检查不能代替数据库并发约束。共享手机号和号码回收不能通过放宽唯一性解决；发生冲突时进入账户恢复或人工安全复核，绝不静默转移。

手机号查找不得使用普通 SHA-256 或明文索引，应使用平台密钥对 `tenant_id + contact_type + 规范值` 生成 HMAC/盲索引。原文仅加密保存，默认接口只返回掩码。密钥轮换必须采用受控双读和重建流程，轮换期间仍须维持跨版本唯一性。

### 5.4 `tenant_member_consents`

追加式授权事件，至少记录：租户、会员、用途、协议版本、`grant`/`revoke`、渠道账号、可信证据方式、幂等键和发生时间。

会员协议、隐私政策、营销短信、营销电话和个性化推荐应使用不同用途，不能一次授权全部推断。

### 5.5 `tenant_member_events`

追加式安全事件，记录客户创建、激活、身份关联/撤销、手机号变更、冻结、匿名化和合并。事件只保存必要摘要，不得把原始手机号、`openid`、会话密钥或令牌写入 JSON、日志或错误信息。

通用 `AuditLog` 继续记录后台操作者和平台操作；会员事件用于客户身份生命周期，两者不能相互替代。

### 5.6 现有订单字段

在以下订单根实体增加可空 `member_id`，并使用 `(tenant_id, member_id)` 约束同租户归属：

- `commerce_orders`；
- 景区票务 `orders`。

不在订单明细、支付、退款、票权、票码、履约、核销或结算表重复保存会员 ID。酒景订单沿用其销售订单归属，酒店预约和入住人仍是履约快照。

现有商业 `CustomerID`、`MiniappCustomerID`、渠道订单关联和订单联系人全部保留。

## 6. 身份生命周期

### 6.1 首次自营登录

1. 现有渠道适配器完成平台登录认证；
2. 服务端解析租户和渠道账号，检查租户状态、渠道状态和 `member_mode`；
3. 现有渠道会话/客户记录按原规则幂等创建；
4. 会员服务按租户、渠道账号、provider 和 subject 盲索引查询映射；
5. 不存在时，在一个事务内创建账户 `status=active`、会员资格 `membership_status=provisional` 的客户和身份映射；
6. 已存在时解析规范会员，更新允许的 `last_seen_at`；
7. 会话只携带服务端解析的会员引用，客户端不能指定或替换。

并发首次登录必须只产生一个身份映射和一个客户记录。

### 6.2 手机号验证和入会

可信手机号只能来自：

- 平台服务端兑换得到的手机号凭据；
- 本系统服务端发起并校验的短信验证码；
- 以后明确批准的等价强验证方式。

用户手填手机号、收货地址手机号、联系人手机号和订单快照不构成验证。

验证流程：

1. 验证短时凭据、防重放和当前登录身份；
2. 单独记录会员协议和隐私授权；
3. 服务端规范化手机号并生成盲索引；
4. 未被占用时绑定当前客户并把 `membership_status` 转为 `active`；
5. 已绑定当前客户时返回幂等成功；
6. 已绑定其他客户时进入显式跨渠道关联流程，不自动转移。

### 6.3 跨渠道关联

用户在另一个自营小程序或 App 完成可信手机号验证后，系统可以将新渠道身份关联到已有会员。

关联前必须证明当前用户控制新渠道身份和已验证手机号。两个已激活会员存在资料或手机号冲突时禁止自动合并，进入安全复核；普通租户管理员第一阶段没有手工合并权限。

自动收敛仅允许当前客户满足 `status=active`、`membership_status=provisional` 且没有其他有效验证联系方式，同时目标客户满足 `status=active`、`membership_status=active` 并持有同一有效可信手机号。任一侧为 `frozen`、`merged`、`anonymized`，或目标为 `membership_status=withdrawn` 时禁止自动收敛，进入安全复核。收敛时：

- 按固定 ID 顺序锁定两侧记录；
- 目标正式会员固定作为规范会员，不按创建时间选择；
- 当前 provisional 客户固定作为被合并方，标记为 `merged` 并指向规范会员；
- 新请求解析到规范会员；
- 保留渠道身份映射原有的 `member_id`，统一由 `MemberService` 的规范会员解析器沿 `merged_into_member_id` 解析到根节点；
- 不改写历史订单上的原会员 ID，会员查询沿合并关系聚合；
- 写入不可变会员事件和授权证据。

这样可以避免批量重写历史订单，也为以后纠错保留证据。订单、后台和游客 API 都不能自行读取映射后跳过规范解析，也不能混用“部分移动身份、部分保留别名”两套策略。

### 6.4 解绑、换号和退出

- 解绑或换号需要近期强认证；
- 不能移除最后一个可恢复身份，除非进入匿名化流程；
- 新手机号验证和占用检查成功后，才能原子撤销旧手机号；
- 被撤销身份保留历史状态，重新登录不能把它静默转给另一会员；
- 撤销营销授权不影响订单履约和会员登录；
- 撤销会员协议或会员服务必需的隐私授权视为退出会员请求：停止新的会员资料处理、跨渠道关联和会员权益使用，`membership_status` 转为 `withdrawn` 并进入受控匿名化/保留流程；
- 退出会员后保留法定交易和审计事实，个人资料按保留策略匿名化，不能删除订单、支付、退款或核销记录。

具体数据保留期限必须在上线匿名化功能前由运营和合规明确；没有策略时不得实现不可逆批量清除。

## 7. 订单关联规则

### 7.1 新订单

合格自营入口创建订单时，订单服务从已认证会话调用会员解析服务，取得同租户规范会员并在服务端写入 `member_id`。客户端提交的 `member_id`、租户、来源或手机号匹配结果一律忽略或拒绝。

订单可以关联 `membership_status=provisional` 的客户，使所有自营入口用户都进入统一管理模块；后台必须清楚区分“待认证客户”和“正式会员”。

`member_id` 只用于客户归属和汇总，不构成本人订单访问权限。订单详情、支付、退款、取消、核销和售后仍使用现有渠道身份、订单归属和业务状态校验。

`member_id` 是非财务客户归属，不得成为目录、原价下单、支付、退款、出票或履约的可用性前提。合格自营入口在正常流程中应确定性解析会员并写入归属；渠道认证失败仍按原渠道规则拒绝请求。若渠道认证已经成功，但会员归属因内部异常或数据冲突无法安全解析，系统不得猜测或写入错误归属，也不得因此改变价格或阻断原业务交易；订单继续使用现有 `CustomerID`、`MiniappCustomerID` 或渠道订单关系完成，并保持 `member_id = NULL`，同时记录可恢复的告警或待处理事实。后续只能依据订单创建时固化的精确渠道身份补充归属。

### 7.2 外部订单

以下订单必须保持 `member_id = NULL`：

- OTA/API 平台订单；
- 分销商、旅行社和团队订单；
- 由外部供应商或外部平台作为销售来源创建、推送或导入的订单；租户自营入口销售但使用外部供应商履约的订单不属于本项；
- 匿名窗口/POS 订单；
- 只有联系人或游客资料、没有合格自营会话的订单。

即使外部订单手机号与某会员相同，也不能关联、认领或补发会员权益。

### 7.3 历史订单

第一阶段不回填历史订单，会员数据统计必须展示有效起始时间。

以后如确有经营需要，只能另行批准“精确身份回填”任务：通过既有 `MiniappCustomerID`、渠道客户 ID 和受信渠道会话建立确定性关联，并记录批次和审计。严禁按姓名、联系人手机号、游客手机号或地址猜测。

### 7.4 合并后的查询

会员详情读取规范会员及其 `merged` 别名下的订单，但不更新历史订单行。退款、支付、履约和核销仍进入订单所属业务域服务，会员中心只能提供只读汇总和深链接。

## 8. 与现有业务的关系

### 8.1 餐饮和电商

同一个微信渠道账号下餐饮和电商已经共用账号级会话，接入统一会员后自然映射到同一租户客户。

第一阶段保留购物车、地址、优惠券和助力活动现有 `CustomerID` 范围；店铺级优惠券是否跨餐饮/电商可用由营销模板的显式适用板块决定，不因为会员合并自动跨渠道共享地址或优惠。会员权益、积分或其他身份相关权益若以后开放，必须单独设计授权、适用业务、退款和冲销规则。

### 8.2 景区票务和酒景产品

只有从租户自营、已认证入口创建的销售订单才关联会员。票种、票码、票权、检票规则、游客实名、酒店预约、入住人、退款和结算不读取会员当前资料覆盖售时快照。

供应商履约、智游宝等上游系统和检票设备不参与会员身份判断。

### 8.3 第三方渠道

第三方订单继续进入各自渠道订单和履约流程。会员中心不显示为会员订单、不提供认领按钮，也不因为租户同时拥有该渠道账号就推定客户关系属于租户。

## 9. 服务边界和 API

建立独立 `MemberService`，唯一负责：

- 客户主档案；
- 渠道身份映射；
- 手机号验证结果接收；
- 授权事件；
- 规范会员解析；
- 冻结、匿名化和受控合并；
- 会员安全事件。

渠道适配器负责认证平台用户，但不决定合并策略。订单服务只调用“解析当前自营客户”接口并持久化经过验证的可空归属。支付、促销、履约、票务、退款和结算服务不得直接写会员映射。

游客 API 只能操作当前会话解析出的客户，不能接受任意会员 ID。建议后续接口方向：

```text
GET  /api/v1/storefront/member/me
POST /api/v1/storefront/wechat/member/verify-phone
POST /api/v1/storefront/xiaohongshu/member/verify-phone
POST /api/v1/storefront/member/consents
POST /api/v1/storefront/member/link-identity
POST /api/v1/storefront/member/unlink-identity
```

租户后台接口始终从 JWT 取得租户，建议方向：

```text
GET  /api/v1/members
GET  /api/v1/members/:id
POST /api/v1/members/:id/freeze
POST /api/v1/members/:id/unfreeze
```

详情接口当前提供跨业务订单数量汇总；订单明细和售后继续通过原业务页面/接口访问，专用会员订单下钻接口留到后续权限和分页契约明确后再开放。

第一阶段不开放租户管理员手工合并、修改验证手机号、把订单挂到会员或跨租户搜索的接口。

## 10. 权限和后台体验

新增独立权限，不能借用普通订单查看权限：

- `members.read`：查看会员基本信息和掩码联系方式；
- `members.sensitive.read`：查看解密后的必要联系方式；
- `members.status.write`：冻结或解冻；
- `members.export`：带原因导出并写审计；
- `members.security.resolve`：未来处理高风险身份冲突，默认仅初始管理员或平台受控角色。

后台统一导航名称建议为“客户与会员”，而不是在餐饮、电商和票务下各建一套会员页面。

列表至少区分：待认证客户、正式会员、已冻结、已合并和已匿名化。详情页展示来源入口、首次/最近访问、掩码手机号、授权状态以及跨业务订单只读汇总；退款、发货、核销等操作必须跳回原业务页面执行。

手机号搜索在服务端规范化并使用盲索引，不能把原始搜索值写入查询日志。普通员工默认只看掩码，导出必须有独立权限、用途和审计记录。

## 11. 隐私和安全规则

1. 新会员敏感标识使用带密钥盲索引，不沿用普通 SHA-256 作为手机号等低熵数据的保护方式。
2. 原始手机号加密保存并记录密钥版本；日志、审计 JSON、错误响应和埋点禁止出现原文。
3. 会员授权、隐私授权和营销授权分开，全部追加记录且可撤销。
4. `member_id` 不是授权凭据，知道会员 ID 不能读取其订单。
5. 客户端不能提交租户、会员、来源分类、渠道所有权或合并目标作为权威事实。
6. 会员冻结限制会员资料维护、跨渠道身份关联以及未来会员权益使用，不替代现有渠道账号、订单和售后授权。第一阶段不得因会员冻结阻断既有渠道身份下的目录浏览、原价下单、历史订单访问、退款或履约，也不得篡改历史交易状态。
7. 平台支持人员跨租户查看必须使用平台专用 scope、明确目标租户、原因和审计，默认掩码只读。
8. 所有身份关联、解绑、换号、冻结、匿名化和合并操作必须幂等并保留不可变证据。

## 12. 迁移和发布顺序

### 阶段 0：入口盘点

- 枚举所有订单和登录入口；
- 给每个入口固化服务端准入分类；
- 先补外部渠道不能伪造会员归属的负向测试；
- 确认手机号验证方式、协议版本和隐私保留策略。

### 阶段 1：加法迁移（已完成本地实现）

- 新增会员表和订单可空字段；
- 不替换、不删除现有客户字段；
- 不回填历史订单；
- `member_mode` 默认关闭；
- 在包含真实历史订单的 PostgreSQL 副本上演练迁移和回滚启动。

### 阶段 2：微信商业小程序试点（已完成代码接入，待真实环境验收）

- 首次登录创建/解析临时客户；
- 餐饮和电商新订单写入会员归属；
- 现有 `CustomerID`、购物车、地址、优惠和售后行为保持不变；
- 先对一个内部租户和一个渠道账号开启，监控重复身份、冲突和空归属率。

### 阶段 3：手机号验证和后台（本地适配完成，真实平台待验收）

- 完成可信手机号、授权、跨入口关联和规范会员解析；微信会话保存加密 `openid` 并在平台响应提供时校验，小红书会话与 `session_key` 解密证据绑定；
- 上线租户隔离的客户列表和详情；
- 暂不开放人工合并和任何积分、等级或余额。

### 阶段 4：其他自营入口（小红书自研入口已完成代码接入，App/官网待开发）

- 小红书自研小程序、App、官网逐个接入；
- 每个适配器必须单独通过准入、租户隔离、身份防重放和外部订单排除测试；
- 不允许通过复制会员表快速接入新渠道。

### 阶段 5：可选权益

只有身份、合并、冻结、匿名化和审计稳定后，才单独设计积分、等级、储值或跨业务权益账本。现有渠道优惠券不得隐式迁移为会员资产。

### 回滚

回滚只关闭租户/渠道的会员功能开关，停止创建新映射和新订单归属。保留新增表、可空字段和审计数据；现有会话、购物车、地址、订单和渠道流程继续按原方式运行。禁止通过降级删除会员表或清空订单归属。

## 13. 验收测试矩阵

### 租户和渠道隔离

- 同一 `openid` 或手机号在租户 A、B 创建独立客户；
- 租户 A 不能读取、搜索、修改租户 B 的会员、身份或订单汇总；
- 不能把其他租户渠道账号映射到当前会员；
- 冻结或关闭租户后，自营入口不能创建或更新会员。

### 身份和并发

- 并发首次登录只创建一个临时客户和一个身份映射；
- 重复登录幂等，只更新允许的访问时间；
- 相同 provider subject 位于不同渠道账号时不自动合并；
- 未验证手机号、相同姓名和订单联系人永不触发关联；
- 手机号碰撞不静默转移；
- 冻结、已退出、已合并或已匿名化客户不能成为自动关联目标；provisional 客户即使创建更早，也不能覆盖已有正式会员成为规范会员；
- 合并解析无环、无分裂规范会员。

### 入口准入

- 同一微信小程序的餐饮、电商订单属于同一客户；
- 不同自营入口只有完成可信验证后才关联为同一正式会员；
- 自研小红书会话订单可关联，纯平台回调/导入订单保持空；
- OTA、分销、旅行团队、外部销售来源、窗口和人工导入订单全部保持空；自营销售加外部供应商履约仍可关联；
- 伪造 `member_id`、来源或渠道类型被拒绝或忽略并留审计。

### 订单兼容

- 现有购物车、地址、促销、支付、退款、出票、核销和结算测试保持通过；
- 迁移前订单语义不变；
- 会员合并不更新订单、联系人、支付、票权、履约和结算事实；
- 禁用会员功能后原 storefront 和渠道流程继续可用；
- `member_id` 不能绕过本人订单访问和售后权限。

### 隐私和后台

- 手机号验证凭据过期、重放和跨身份使用全部失败；
- 普通员工看不到完整手机号；
- 手机号原文不出现在日志、错误和审计 JSON；
- 导出要求权限、原因并生成审计；
- 撤销营销授权不影响订单履约；
- 匿名化不删除法定交易和核销事实。

## 14. 明确不在首期范围

- 外部渠道订单认领或自动转会员；
- 根据联系人、游客或收货人手机号匹配会员；
- 人工把任意订单挂到会员；
- 租户管理员随意合并或拆分会员；
- 跨租户会员、平台全局会员或供应商共享会员；
- 跨业务混合订单；
- 积分、等级、成长值、储值、会员价、通用券和自动营销；
- 共享地址簿或把现有渠道优惠自动迁移到会员账户；
- 用会员当前资料覆盖历史订单和履约快照。

## 15. 后续开发回顾清单

任何会员相关实现、审查或交接开始前必须先确认：

1. 本次入口是否经过服务端认证，并明确属于租户自营还是外部渠道；
2. 租户、渠道账号和会员归属是否全部由服务端上下文推导；
3. 是否保留现有渠道客户字段和订单快照；
4. 是否错误使用姓名、联系人手机号或客户端来源建立关联；
5. 是否新增跨租户、跨渠道、并发首次登录和外部订单排除测试；
6. 是否把会员 ID 当成订单访问、退款或核销授权；
7. 是否泄露原始手机号、渠道用户标识、令牌或会话密钥；
8. 是否意外让积分、优惠、支付、履约、票务或结算服务写会员映射；
9. 迁移是否只做加法并在生产形态 PostgreSQL 数据上演练；
10. 文档、实现和测试不一致时，是否先停止扩展并修正冲突。

本文未明确开放的身份来源、合并方式、权益类型和历史关联一律视为未授权范围，不能以兼容逻辑或前端开关绕过。

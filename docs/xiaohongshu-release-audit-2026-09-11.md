## 代码发现与上线结论

### F1：P1，支付/出票查单队列可能长期跳过后续订单

- 位置：`backend/internal/service/xiaohongshu_order_service.go:662`；调度入口 `backend/cmd/main.go:250`。
- 触发：至少 21 笔符合查询条件的链接，前 20 笔持续未付款或已付款但待签发；查询每轮能在下次调度前完成。
- 当前实现：每 30 秒运行，按 `id ASC LIMIT 20` 选择 `last_queried_at < now - 20秒` 的记录。前 20 笔在下一轮又满足条件，继续占据整个批次。处于 `creating` 且已有持久下单操作的记录被选中后直接跳过，也会占据批次。
- 后果：第 21 笔及后续订单可能长期得不到后台查单、出票或取消恢复。游客主动打开详情可另行触发查询，但离开小程序的已付款游客不能依赖此路径。现有 webhook 消费不提供所有支付订单的独立推进保障。
- 证据：主线程使用本地 PostgreSQL 纯 SELECT CTE，构造 21 条逻辑记录；第一轮选取 1–20，更新查询时刻为 t0+1 秒后，在 t0+30 秒再次执行同一选择条件，仍返回 1–20，`order_21_selected=false`。这是选取算法复现，未修改真实订单，也不宣称已执行 21 笔真实平台交易。
- 最小方向：按最久未查询优先推进（包括 NULL 的明确优先级），并从链接查询批次排除由独立下单操作处理的 creating 行；增加超过单批次的恢复回归。无需为此引入消息中间件。

### F2：P1，账号售后隔离与新下单之间存在并发空档

- 位置：`backend/internal/service/xiaohongshu_order_service.go:306`、`:390`；对照 `backend/internal/service/xiaohongshu_refund_coordination_service.go:78`。
- 触发：新下单在事务外查到账号无 hold；随后可信外部售后回调创建账号级 hold 并提交；原下单继续进入写事务。
- 当前实现：下单事务没有重新检查账号 hold，也没有用账号行锁与回调串行化。促销的 `loadMiniappPromotionAccount` 仅检查能力和账号状态，不检查售后 hold。数据库写协调器允许多个事务并行。
- 后果：账号已暂停新单后仍可能新增订单、占用库存并发起平台下单；后续核销会被账号 hold 拦截，出现仍可购买但暂不能使用的订单。不能把此问题描述为已绕过核销保护。
- 证据：退款 agent 与主线程分别核对调用链、账号锁和事务边界；为静态并发时序证明，本轮未向真实平台发送回调或订单。
- 最小方向：新下单事务内与售后隔离使用相同账号锁，重新检查 hold，再创建订单；沿用一致锁顺序并增加回调/下单并发回归。

### F3：P1，下单结果不明后修改选择，重试可能支付旧订单

- 位置：`xiaohongshu-miniapp/xiaohongshu-miniapp/pages/order/confirm.js:109`、`:269`、`:306`；`backend/internal/service/xiaohongshu_order_service.go:154`、`:293`、`:395`。
- 触发：第一次选择一张 9 月 20 日门票并提交，服务端落单成功但响应丢失；页面恢复可操作，游客改为两张 9 月 21 日门票，点击重试。
- 当前实现：页面重用同一个 `orderRequestId`，数量与日期允许修改；服务端幂等查询只按游客、账号、租户和请求号匹配，直接返回原订单，没有校验新请求的商品、数量、日期等是否与原订单一致。前端随后直接把返回的旧订单传给支付 SDK。
- 后果：界面选择与实际购买的日期/数量可能不一致。此问题不是重复扣款证明，而是错误票权及金额确认风险。
- 证据：前端 agent 用真实确认页源码在 VM 中复现，两次请求分别为 `quantity=1/use_date=2026-09-20` 和 `quantity=2/use_date=2026-09-21`，请求 ID 均为 `same-request-id`；主线程复核了页面编辑条件、错误分支与服务端提前返回路径。
- 最小方向：结果不明先恢复原订单并展示实际订单信息；服务端对同请求号的业务参数做一致性校验。不能仅在网络失败后换新请求号重下，否则可能产生重复订单与库存占用。

### F4：P2，商品配置一次保存可能只完成一半

- 位置：`admin/src/views/ChannelView.vue:818`；`backend/internal/service/channel_service.go:461`。
- 触发：后台修改名称、外部编码或售价，第一步 PATCH 映射成功，第二步 PUT 发布配置因网络或校验失败。
- 后果：页面显示保存失败，但映射已经更新，旧审核状态已重置为 pending，商品可能从可售目录退出。审核重置本身是必要保护，问题是一次界面保存包含两个独立提交且没有明确告知部分成功。
- 证据：主线程复核了两个顺序请求及第一步事务内的审核重置；本轮未修改生产商品。
- 处理方向：至少在失败时重新读取并明确显示实际保存状态；后续若合并保存接口，应保留发布字段修改后重新审核的规则。不作为普通票首发的核心资金阻断项。

### F5：P2，上传后未引用的图片没有应用内回收路径

- 位置：`backend/internal/service/xiaohongshu_image_store.go:27`、`backend/internal/service/xiaohongshu_storefront_service.go:30`；`admin/src/views/ChannelView.vue:800`。
- 上传立即产生独立文件，配置保存另行执行；取消保存、反复替换或清除引用不会回收旧文件。仓库相关存储、服务、脚本中未找到清理流程。
- 影响是长期存储累积，本轮没有发现磁盘容量告警；不据此阻断首发。不应直接删除旧图片，清理需考虑历史引用与合理保留时间。

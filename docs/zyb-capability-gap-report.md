# 智游宝主要能力差距报告

报告日期：2026-07-30

当前项目基线：`0b3f7c4` (`codex/embedded-sqlite-hardening`)

对照资料：`E:\code\zyb\2020.4.30智游宝门票接口文档 分时.docx`

## 1. 结论

当前项目已经形成一套可运行的自营票务核心：多租户、商品、订单、微信/支付宝/现金支付、总库存与日库存、核销规则、设备鉴权、OTA 下单/取消/查询、分销资金和基础经营报表均已具备。

但它还不能作为智游宝的直接替代品投入多渠道生产。阻断替代的不是基础下单，而是订单创建后的完整履约闭环：渠道回调、部分退票及审核、游客票码交付、实名制逐人票、分时库存扣减、到付订单状态机，以及异常订单的自动对账与补偿。

按文档中的 22 项能力统计：

- 等价覆盖：1 项
- 部分覆盖：10 项
- 尚未覆盖：11 项

这里的“部分覆盖”通常表示内部已有数据或操作，但没有智游宝级别的外部接口、异步状态或运营闭环，不能按已完成计算。

## 2. 对接文档逐项对照

| 文档能力 | 当前状态 | 判断依据与缺口 |
|---|---|---|
| `FS_STOCK_REQ` 分时库存查询 | 部分覆盖 | 有总库存、日库存和分时时段配置；OTA 无按日期/时段查询库存接口，订单扣减逻辑也未按 `time_slot_config` 扣减具体时段。 |
| `SEND_CODE_REQ` 已支付订单 | 等价覆盖 | OTA 外部单号幂等创建后自动置为已支付，并生成内部票码。 |
| `CREATE_UNPAY_ORDER_REQ` 创建未支付订单 | 部分覆盖 | 窗口订单可创建为 `unpaid`，但 OTA 没有“创建待支付订单”模式，也没有标准外部支付状态协议。 |
| `PAY_ORDER_REQ` 确认未支付订单 | 部分覆盖 | 内部支付接口可将订单置为已支付；没有面向渠道的幂等确认接口和外部订单语义。 |
| `CANCEL_UNPAY_ORDER_REQ` 取消未支付订单 | 部分覆盖 | 服务层能取消并回补库存，但管理端没有订单取消路由，OTA 取消同时兼容已支付订单，协议边界不等价。 |
| `CHECK_STATUS_QUERY_REQ` 查询检票情况 | 部分覆盖 | 内部有票状态和核销记录；没有供 OTA/分销商按外部子订单查询的接口。 |
| `SEND_CODE_CANCEL_NEW_REQ` 取消已支付订单 | 部分覆盖 | OTA 可整单取消未核销的已支付订单；没有后台操作入口、退款支付联动和异步审核状态。 |
| `SEND_CODE_IMG_REQ` 发码图片 | 尚未覆盖 | 只返回原始票码字符串，没有可下载的二维码/条码图片接口。支付二维码不属于门票发码。 |
| `SEND_SM_REQ` 发送短信 | 尚未覆盖 | 没有短信供应商、模板、发送记录、重试和补发接口。 |
| `RETURN_TICKET_NUM_NEW_REQ` 部分退票 | 尚未覆盖 | 没有按子订单、票或身份证退部分数量的模型和接口。 |
| 订单完结通知 | 尚未覆盖 | 订单可在权益耗尽后变为 `completed`，但没有向下单渠道发送签名回调、重试和送达记录。 |
| `QUERY_ORDER_NEW_REQ` 订单查询 | 部分覆盖 | OTA 可按外部单号查单，后台可分页搜索；返回协议缺少辅助码、退票数、已核销数、座位等完整履约信息。 |
| 退票审核通知 | 尚未覆盖 | 没有退票申请/审核状态机，也没有审核结果回调。 |
| 退票流程 | 尚未覆盖 | 缺少“申请、待审核、成功/失败、游客退款、库存与分销资金回补”的一致性闭环。 |
| `QUERY_SUB_ORDER_CHECK_RECORD_REQ` 核销明细 | 部分覆盖 | 数据库保存成功和拒绝记录；没有按外部子订单开放的明细查询接口。 |
| `CANCEL_SPOT_ORDER_REQ` 到付单取消 | 部分覆盖 | 窗口现金订单和一般取消能力存在，但没有独立的到付订单协议与状态机。 |
| `QUERY_RETREAT_STATUS_REQ` 退票结果查询 | 尚未覆盖 | 没有退票批次号、审核中/通过/拒绝状态及查询接口。 |
| 核销通知 | 尚未覆盖 | 核销后不向原下单渠道回调；实名制核销也不能回传证件集合。 |
| `QUERY_IMG_URL_REQ` 二维码链接 | 尚未覆盖 | 没有受控票码链接、访问鉴权、有效期或吊销机制。 |
| 到付订单确认/取消通知 | 尚未覆盖 | 没有到付订单对外回调和重试机制。 |
| `QUERY_SHORT_IMG_URL_REQ` 二维码短链接 | 尚未覆盖 | 没有短链接服务、有效期和访问审计。 |
| `QUERY_SPOT_ORDER_REQ` 到付订单查询 | 部分覆盖 | 一般订单可查询，但没有 `valid/invalid` 到付状态、景区子单结构和对应外部协议。 |

## 3. 主要缺口与优先级

### P0：阻断生产替代

1. **售后与退款状态机**

   需要支持整单/部分退票、按票或实名证件退票、退票批次、异步审核、支付退款、库存回补、分销资金回补，以及全过程幂等。目前“取消订单”不能替代退票。

2. **渠道事件通知中心**

   订单完结、核销、退票审核和到付状态变化都需要可靠通知原渠道。至少需要签名、事件唯一键、持久化 outbox、失败重试、送达确认、人工重放和审计记录。

3. **真实分时库存**

   当前界面可配置时段，但下单只扣总库存或日期库存。需要建立“产品 + 日期 + 时段”的库存实体，并让查询、预占、支付、取消、退票共享同一套原子扣减规则。

4. **实名制逐人票**

   `Ticket` 虽有游客姓名和证件字段，但下单没有接收并校验每位游客资料，生成票时也没有写入身份证。需要一人一证一权益的关联、证件脱敏/加密、重复购票限制和按证件退票。

5. **票码交付**

   需要门票二维码/条码图片、受控长链接、可选短链接和短信补发。链接应支持过期、吊销、防枚举和访问审计，不能直接暴露数据库票码。

### P1：渠道规模化前必须补齐

6. **外部订单生命周期协议**

   把“创建待支付、确认支付、取消待支付、取消已支付”拆成明确且幂等的接口；增加未支付超时自动关闭。智游宝文档约定未支付订单 30 分钟关闭，当前订单会长期停留在 `unpaid`。

7. **履约查询 API**

   对外提供订单详情、票状态、核销汇总和核销明细，统一使用稳定的外部主/子订单号。辅助码、票码、已核销数、已退数和有效期应有明确字段。

8. **到付订单状态机**

   区分预付、备用金、平台支付和现场到付；到付单需要待确认、有效、无效/取消等状态及通知。当前 `window + cash` 只是收银方式，不等价于渠道到付单。

9. **异常补偿与对账**

   文档明确要求超时后查单、两小时内多次查询而不是直接退款。项目需要定时扫描不确定状态、支付/订单/渠道三方对账、人工处置队列和完整操作审计。

10. **外部接口产品化**

    当前 OTA 接口只有商品列表、下单、取消、查询。正式替代还需要版本管理、稳定错误码、分页与限流规范、签名 SDK/示例、沙箱、回调配置、IP/密钥轮换和接口监控。

### P2：运营成熟度

11. **售后与通知运营台**：待审核退票、失败回调、短信失败、异常支付和对账差异需要可筛选、可重试、可审计的后台页面。

12. **报表深化**：现有销售趋势、商品排行和渠道占比是起点；后续需要核销率、退票率、未使用票、渠道应收应付、结算周期和日结对账。

13. **数据治理**：实名信息需要字段级加密、脱敏展示、访问日志、保留期限和删除策略；票码与回调载荷也应按敏感数据处理。

## 4. 建议的后续讨论顺序

后续开发不应按页面数量推进，而应按业务闭环推进：

1. 先确定外部订单、子订单、票、支付、退款和渠道事件的统一状态机。
2. 再实现渠道 outbox 与查询接口，使每次状态变化都可查询、可通知、可补偿。
3. 在同一事务边界内补齐分时库存、部分退票、支付退款和分销资金回补。
4. 最后接入短信、票码链接、短链接和运营后台。

第一阶段验收标准应是一条完整链路：渠道下单 -> 支付 -> 发码 -> 核销 -> 回调；以及渠道下单 -> 部分退票 -> 审核 -> 原路退款 -> 回调。两条链路都必须具备幂等、重试和对账能力。

## 5. 报告边界

本报告只以《智游宝平台发码验码接口开发指南（分时）》为权威对照。该文档是分销商发码验码接口，不是智游宝后台全部产品说明，因此会员营销、旅行社团队、导游、酒店/套票、电子发票、闸机厂商协议、结算清分等是否属于实际替代范围，仍需结合景区当前使用的智游宝菜单、合同模块和真实业务流程另做盘点。

原 DOCX 可完成结构化内容提取，但当前机器未安装 LibreOffice，未进行页面渲染与版式检查；这不影响接口能力清单和代码差距结论。

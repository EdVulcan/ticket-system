### 2026-09-09 店铺随机立减（本地实现，未部署）

管理入口为“渠道管理 → 小红书账号 → 随机立减”。默认关闭，可按商品名称选择参与商品，设置随机金额上下限、有效分钟数及再次获得间隔天数。立减属于当前店铺的游客机会，自动获得、自动用于下一笔符合条件的订单；不需要领券或选券，多份票只减一次。

- 获得时保存金额、有效期与再次获得时间。未用过期仍进入原定间隔，重新进店、换商品、开关活动或改设置不重抽、不重置已有机会。关闭活动或移除商品立即阻止未提交使用；重新启用仍沿用原机会和时间。
- 下单按服务端报价确认价格，金额或资格变化时要求游客重新确认，不静默恢复原价扣款。订单、库存、立减占用、游客幂等关联及加密平台请求同事务提交。已提交的订单保留优惠价直到其支付流程结束；机会本身到期不改价。
- 退出支付页不会释放。支付状态未知、网络中断或仅令牌过期都保留占用；平台明确未付关闭才取消并释放。释放后只能在原有效期且活动/商品仍可参与时继续用。成功支付后消耗，退票退款不恢复机会。
- 服务端按租户、渠道账号和游客隔离身份，前端仅提交商品、数量及报价凭据。POST `/storefront/xiaohongshu/promotion` 自动获取机会，POST `/storefront/xiaohongshu/order-quote` 只报价、不生成新机会；上述路径均位于 `/api/v1`。
- 支付协议采用[订单同步 DC948963](https://miniapp.xiaohongshu.com/doc/DC948963)的商品行总额：`sale_price = 原单价 × num`，`discount_infos = [{name: "限时随机立减", price: 立减分, num: 1}]`，`real_price = sale_price - 立减分`，`price_info.order_price = real_price`。不额外写 `discount_price` 再扣一次。支付查询继续精确核对应付金额。
- schema 116 保存订单原价、立减和每张票的实付分摊。例：两份各 100 分，整单立减 1 分，应付 199 分，两票分摊 100/99 分；整单退款为 199 分。卖方承担立减，供应商结算价、佣金及履约规则不变；最低售价和每份一分下限仍生效。历史 NULL 分摊继续走旧单价，历史加密平台请求不回写。
- 当前只允许已审核的普通团购门票参与；整单一码限一份，普通一人一码可多份。立减订单支持既有退款/补打，暂不支持改变价格分摊的改期、换票或作废，提示退票后重购。

正式启用前仍需验证：平台接受一次行级立减、多份券的金额分摊及对应退款、回调/主动查询收敛、退款到账、真机倒计时及网络中断恢复。未通过前保持活动关闭；HTTP 模拟服务只证明本地请求和账务一致性。旧未发送订单若保存了不满足原总额与实付关系的请求，将保留现场并报错，不能自动覆盖其销售快照。

立减订单首次出票按平台券 `pay_amount` 匹配本地票的固定实付分摊，不依赖平台券数组顺序；缺失或不一致则保留已支付事实，进入出票人工核对，不展示可核销票码。已有绑定再次查询时同样核对金额，不自动重绑或重写分摊。

这里将普通团购券 `pay_amount` 的可用性列为活动正式启用前的明确验收条件，尚不能认定平台对所有订单都会返回此值；若实际回包不满足条件，应保持活动关闭并按官方确认的协议调整，不能将缺失值猜成均摊或直接绕过校验。支付与关闭并发时，在锁住订单关联及订单后重新检查终态；取消、退款等已结束订单拒绝过期的支付查询结果。带立减及零立减订单的双向延迟响应测试均检查支付、库存和机会只按已落库终态变化一次。

本地验证记录：后端 `go test ./... -count=1 -timeout 12m` 通过；schema 115→116 升级/重跑及归属保护测试通过；小程序 Node 测试 65 项通过；管理端活动配置 Playwright 2 项及类型检查/生产构建通过。专项测试覆盖同游客并发领取/下单、原机会过期、关闭重启活动、锁价、退款后不恢复、分摊尾差及商品销售报表。Windows 当前未安装 C 编译器且 CGO 关闭，`-race` 未能运行，需后续 GitHub 既有 `backend-race` 验证；本批未推送或部署。

### 2026-09-09 误核销后整单退款（本地实现，未部署）

- 官方[核销经营说明（DC137160）](https://miniapp.xiaohongshu.com/doc/DC137160)明确团购券支持核销后整单退和部分退，交易时间超过一年不可提交退款。该平台能力不改变本项目的权限边界：只复用履约供应商初始管理员的既有已核销退票例外，且当前限制为单一普通团购券商品订单的整单、全额退款；游客自助、普通管理员、分销商和平台人员仍不允许对已使用票退款。
- 申请前必须精确确认本地完成核销、平台 `verify_id`、券/订单/租户/渠道账号和售后快照一致。复用既有[售后 add（DC767572）](https://miniapp.xiaohongshu.com/doc/DC767572)与 get 查询，不假设另有“撤销核销”接口，也不先改写票为未使用。平台受理、未知或失败时保留原核销事实；仅平台退款成功后，现有原子退款流程冲销有效核销投影并失效票券，同时保留原核销、`verify_id`、审计及历史结算依据，不恢复历史容量。
- 本轮不开放部分退、酒店/预约券、混合支付或自动已使用退款；不需要数据库迁移。真实核销后退款、退款回调和现场报表/结算口径尚未通过平台验收，不能据本地实现宣称生产可用。以下较早“只支持未核销普通团购券”的范围说明以本条为准。
- 本地验证：后端 `go test ./... -count=1 -timeout 10m`、后台 `channel-order-refund.spec.ts` 页面测试及 `npm run build` 通过。新增回归覆盖实际核销流程生成的凭据、非初始管理员与跨租户拒绝、核销证据不匹配、退款待确认/失败时保留核销、成功后冲销、重复请求与退款后再次核销拒绝。部署后应以一笔小额正式订单验收“核销 → 初始管理员退款 → 到账”，同时确认平台券状态、商品资源及结算明细；`refund_rule_type=1` 沿用现有请求，不把其平台资源处理等同于本地历史容量回补。

- 回调成功落库后立即发出进程内唤醒通知，现有执行器直接处理到期任务，30 秒扫描仅作为普通查询和持久任务恢复的兜底。领取任务时清空 `next_attempt_at`；执行期间到达的回调仅写入立即复查时间并重置尝试次数，不修改 `processing` 或 `locked_at`。当前请求返回非终态/暂时失败时保留这一提示，下一次领取消费；成功、明确失败和安全复核结果优先。没有新增消息中间件、WebSocket、回调直接结账或 HTTP 查订单时触发资金动作。进程内唤醒不覆盖其他实例或崩溃租约；平台通知/查单延迟、积压任务耗时可能延长同步时间，不承诺到账后固定秒数内完成。
- 小程序与后台退款中的页面使用现有只读订单接口自动刷新，确认终态后停止；后台增加退款中展示，保持订单原支付状态及原筛选条件，不把受理当作退款成功。重新编译/上传小程序与后端部署是不同发布步骤。

## 2. 已确认的业务语义

- 普通 `/mp` 商品、订单和查询接口使用销售租户自有小程序 `appid` 和 `appsecret` 获取并缓存调用凭证；这组凭据不能用于预售券 `/component` 接口。
- 预售券预约和预约状态同步必须使用服务商 `appid` 与已授权销售小程序的组件访问凭据。授权凭据未配置、过期或无法刷新时，预约必须拒绝外部请求并保留可恢复的本地任务，不能伪造成功。
- 景点身份同步生活服务商品时必须关联小红书 POI；团购、预售券和日历商品分别使用 `product_type=1/2/3`。
- 本地生活担保支付必须配置结算方式。优先按景区实际资质选择总店或门店结算，不由客户端自行提交。
- 本系统先创建外部订单，再将订单及小程序订单详情路径同步给小红书；小红书返回 `order_id`、`pay_token` 和支付类型。
- 支付结果以小红书担保支付订单查询、支付回调和本地订单状态共同幂等收敛，不能仅凭前端支付成功页面出票。
- 小红书返回的凭证码必须绑定到本项目既有票权；闸机扫码后，服务器调用小红书核销接口，取得 `verify_id` 后再完成可追溯核销。
- 小红书券核销使用持久协调记录，不把外部 HTTP 调用放进本地票务事务。正常路径是“本地预校验/占用 -> 外部核销 -> 保存 `verify_id` -> 本地核销”；进程在 `prepared`、外部确认或本地待提交阶段退出时由 worker 恢复。超时、空响应、5xx、网络错误和无法判断的结果进入 `external_unknown`，不开闸且不自动重发；已确认外部核销但本地提交失败时只重试本地提交。
- 同一设备的 `request_id` 按数据库唯一约束幂等；同一券只能有一条有效协调记录。不同请求号不能抢占正在处理的协调记录，已完成请求直接重放同一条本地核销事实。原始小红书券码只在服务端解密后发往官方接口，不写入设备核销记录或日志。
- 官方售后接口支持全额及部分退款；本项目当前只适配未核销普通团购券的整单全额退款，不能直接套用其他支付渠道的部分退票规则。具体边界以本文 2026-09-08 补充为准。
- “先购买、后预约入住”的酒景套餐必须使用预售券商品类型。购买时只产生担保支付订单和逐份预约权益；游客选定入住日期后，系统同时校验票库存和连续房晚，调用小红书预约接口，成功后才生成可核销票码。取消、改约、退款和过期必须保留平台预约状态同步事实。

## 3. 与现有渠道模型的映射

| 小红书事实 | 本项目事实 |
|---|---|
| 小程序应用 | 租户独立 `ChannelAccount` |
| 外部商品和 SKU | `ChannelProductMapping` 与售卖时产品版本快照 |
| `out_order_id` | 本项目销售订单号 |
| 小红书 `order_id` | 渠道协议关联，不覆盖本地订单号 |
| `open_id` | 按渠道账号隔离的游客标识；哈希检索、密文保存，不作为后台账号 |
| 凭证码 | 绑定到对应供应商、景区和票权，不成为跨景区通用票 |
| `verify_id` | 核销外部事实编号，与本地核销记录幂等关联 |
| 平台结算结果 | 渠道对账事实，不覆盖供应商核销收入和上下游结算账本 |

小红书商家应用凭据必须按销售租户单独加密保存。景区自营使用景区供应商租户的应用；未来分销商自有小红书账号接入时使用分销商租户的应用，但履约票权仍属于产品对应的供应商和景区。服务商 `appid`、授权小程序标识及组件访问/刷新凭据属于独立配置，不能复用商家 `AppID/AppSecret` 字段。

### Booking status and webhook boundary (schema 86)

- `refund_status_sync` is a durable presale-booking operation only. It sends booking status `4` after an independently completed local user after-sale and must never be interpreted as, invoke, or confirm a Xiaohongshu funds refund.
- Schema 86 migrates legacy `refund` booking operations and their conventional `xhs:refund:` operation keys to `refund_status_sync`. The migration protects the globally unique key before renaming, so durable legacy tasks are preserved.
- Webhooks remain signature-verified, decrypted, encrypted at rest, and idempotently stored in the inbox. Only explicitly recognized non-financial events remain pending. After-sale/refund and unknown business events are stored as `manual_review`; they cannot change local payment, ticket, entitlement, inventory, or settlement facts.
- Deferred booking commands and the admin/reconciliation worker use `XiaohongshuBookingService`; `MiniappService` remains only the HTTP compatibility facade for existing storefront routes. Payment/order reconciliation is kept separate from the booking Saga.

### 2026-09-03 self-developed miniapp connection check

- After a miniapp is unbound from a service provider, the merchant self-developed `/mp` path can be checked independently. The admin channel page now exposes “连接测试”, backed by `GET /api/v1/channel-accounts/:id/xiaohongshu-diagnosis`.

1. 在渠道管理页保存商家自研小程序的 `AppID/AppSecret`，运行环境选择测试环境，并先运行“连接测试”。

6. 同一订单重复查询、应用重启后查询、支付令牌过期三种情况都验证一次。

## 6. 生产验收门槛

1. 商品同步成功且在正确景区 POI 下可见，不影响其他租户产品。
2. 小程序下单只提交本项目签发的产品和价格事实，客户端不能篡改金额、供应商或景区。
3. 小红书支付成功后，本地订单、支付、履约单和票权幂等生成；超时、重复查询和进程重启不重复出票。
